7.1 Controle de versões em documentos administrativos

Qual é a versão certa?

Imagine que o setor de compras encontra estes arquivos em uma pasta:

procedimento-compras.txt
procedimento-compras-novo.txt
procedimento-compras-final.txt
procedimento-compras-final-certo.txt
procedimento-compras-agora-vai.txt

Todos parecem importantes. Mas qual contém a regra atual? Quem alterou? Quando? O que mudou? E se uma regra correta tiver sido substituída por engano?

Antes de usar tecnologia

  1. Que risco administrativo existe quando ninguém sabe qual é a versão vigente?
  2. Que tipo de problema isso pode causar em compras, aprovações e auditorias?
  3. Renomear arquivos manualmente resolve o problema por completo?
Ligação com Tecnologia e Gestão: tecnologia só faz sentido quando ajuda a organizar um processo real. Aqui, o problema não é “aprender Git”; é manter regras administrativas com histórico, evidência e possibilidade de recuperação.
2

Crie o procedimento

Comece pelo processo administrativo. A ferramenta entra depois.

1. Crie a pasta de trabalho

Crie uma pasta chamada procedimento-compras.

Dentro dela, crie o arquivo procedimento-solicitacao-compras.txt.

2. Digite a primeira versão

PROCEDIMENTO DE SOLICITAÇÃO DE COMPRAS

Objetivo
Organizar as solicitações de compras da empresa.

1. O funcionário identifica a necessidade de compra.
2. A solicitação é encaminhada ao responsável pelo setor.
3. O setor de compras consulta fornecedores.
4. A compra é aprovada pelo responsável.
5. O setor de compras realiza o pedido.
6. O material recebido é conferido.
7. A conclusão da compra é registrada.

Salve o arquivo.

Se o arquivo abrir novamente com esse conteúdo, está correto. Você já tem um procedimento administrativo funcional. Agora surge outra necessidade: guardar esta versão de forma confiável antes de alterá-la.
3

Guarde a primeira versão

Transforme a pasta em um histórico controlado.

Por que precisamos de outra solução?

Poderíamos duplicar o arquivo e escrever “versão 1” no nome. Isso funciona por pouco tempo, mas não registra automaticamente o histórico nem mostra com clareza o que mudou. É aqui que o Git passa a ter utilidade.

Abra o terminal na pasta

No Explorador de Arquivos, abra a pasta procedimento-compras. Clique na barra de endereço, digite cmd e pressione Enter.

Execute:

git init

Depois:

git status

O Git deverá indicar que existe um arquivo ainda não registrado.

Agora execute:

git add .
git commit -m "Cria procedimento inicial de compras"
Se o commit foi criado, está correto. A primeira versão do procedimento agora faz parte do histórico.
4

Primeira mudança administrativa

Uma nova regra cria a necessidade de uma nova versão.

A empresa mudou a política de compras

A partir de agora, antes de realizar uma compra, o setor deve obter três cotações.

Altere o documento

Troque a etapa 3 por:

3. O setor de compras obtém três cotações de fornecedores.

Salve. No terminal, execute:

git status

O Git deverá indicar que o arquivo foi modificado.

Registre a nova versão:

git add .
git commit -m "Exige tres cotacoes antes da compra"
Encadeamento: uma regra do processo mudou → o documento mudou → uma nova versão precisou ser registrada.
5

Segunda mudança administrativa

O histórico começa a adquirir valor gerencial.

Nova regra de aprovação

Compras acima de R$ 5.000 agora precisam de aprovação da gerência.

Atualize o procedimento

Depois da etapa das cotações, inclua:

4. Compras acima de R$ 5.000 precisam de aprovação da gerência.

Renumerar as etapas seguintes faz parte da atualização do documento.

Antes de registrar, execute:

git status

Depois:

git add .
git commit -m "Inclui aprovacao da gerencia acima de 5000 reais"
Se o novo commit foi criado, está correto. Já existem pelo menos três momentos diferentes do mesmo procedimento.
6

O que mudou?

Antes de registrar uma alteração, confira exatamente o que foi mexido.

Uma pequena conferência evita um grande problema

Altere temporariamente uma frase do procedimento, mas não faça commit ainda. Agora precisamos responder: o que foi alterado?

Execute:

git diff

As linhas removidas e adicionadas deverão aparecer no terminal.

Leia o resultado e localize a frase que você modificou.

Se você consegue apontar a linha alterada, está correto. Em Administração, isso representa conferência antes de formalizar uma nova versão.
7

Quem fez o quê e quando?

Agora o histórico responde perguntas que nomes de arquivos não respondem bem.

Desfaça a alteração temporária manualmente e salve o arquivo. Depois execute:

git log --oneline

Você deverá ver uma lista com os registros feitos até aqui.

Leia como um profissional de Administração

Cada registro representa uma mudança formalizada no procedimento. A mensagem do commit deve explicar a alteração de maneira objetiva, como um pequeno registro de ocorrência do processo.

Rastreabilidade: agora existe evidência de que o procedimento evoluiu, em que ordem as mudanças ocorreram e qual era a finalidade de cada alteração.
8

Algo foi alterado por engano

O valor do histórico aparece de verdade quando precisamos corrigir um erro.

Simulação

Alguém altera a regra e escreve que compras acima de R$ 50.000 precisam de aprovação da gerência, quando o valor correto continua sendo R$ 5.000.

Faça essa alteração errada, salve e registre:

git add .
git commit -m "Altera limite de aprovacao"

Agora execute:

git log --oneline

Localize o registro imediatamente anterior ao erro e copie os primeiros caracteres de seu identificador.

Não apague o histórico. Em um processo rastreável, até a correção deve ficar registrada.
9

Recupere a versão correta sem apagar a história

Use o histórico como fonte confiável para restaurar o documento.

Recupere o arquivo da versão anterior

Substitua IDENTIFICADOR pelo código que você encontrou no histórico:

git restore --source=IDENTIFICADOR procedimento-solicitacao-compras.txt

Abra o arquivo e verifique se o limite voltou para R$ 5.000.

Se estiver correto, registre a correção:

git add .
git commit -m "Corrige limite de aprovacao para 5000 reais"
Se o valor correto voltou e a correção aparece como um novo commit, está correto. O erro não foi escondido; ele foi identificado e corrigido com rastreabilidade.
10

Leve o histórico para o GitHub

Quando surge a necessidade de manter e consultar o histórico também online, entra o GitHub.

Git e GitHub não são a mesma coisa

Até aqui, todo o histórico ficou no computador. Agora vamos criar uma cópia online para facilitar acesso, compartilhamento e consulta.

1. Crie um repositório vazio no GitHub

No GitHub, escolha New repository. Use o nome procedimento-compras e não adicione arquivos iniciais.

2. Conecte a pasta ao repositório

O GitHub exibirá o endereço do novo repositório. No terminal, dentro da pasta do projeto, execute os comandos indicados pelo próprio GitHub para um repositório existente. Em geral, serão equivalentes a:

git branch -M main
git remote add origin URL_DO_SEU_REPOSITORIO
git push -u origin main

3. Verifique

Atualize a página do repositório no navegador. O arquivo deverá aparecer.

Abra a área de commits para conferir se o histórico também foi enviado.

Se o arquivo e os commits aparecem no GitHub, está correto. O mesmo histórico que você construiu localmente agora também pode ser consultado online.
11

Agora é com você

Mostre que compreendeu o processo, não apenas os comandos.

Nova decisão administrativa

A empresa decidiu que toda solicitação aprovada deve ser concluída em até dois dias úteis após a aprovação.

  1. Decida em que ponto do procedimento essa regra deve aparecer.
  2. Faça a alteração.
  3. Confira o que mudou antes de registrar.
  4. Registre uma nova versão com uma mensagem clara.
  5. Envie a atualização ao GitHub.
  6. Mostre no histórico qual registro corresponde a essa mudança.

Checkpoint final

  1. Por que guardar apenas arquivos chamados “final”, “novo” e “certo” é frágil?
  2. Qual é a diferença prática entre conferir uma alteração e registrar uma versão?
  3. Como o histórico ajuda em auditoria, controle interno e gestão de processos?
  4. Por que uma correção deve ser registrada em vez de simplesmente esconder o erro anterior?
  5. Em quais outros documentos administrativos esse método poderia ser útil?
Leve para a Administração: controle de versões não é assunto exclusivo de programação. É uma forma de manter histórico, responsabilidade, evidência e possibilidade de recuperação em documentos que mudam ao longo do tempo.
