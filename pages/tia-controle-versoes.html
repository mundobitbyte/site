7.1 Controle de versões em documentos administrativos

Qual é a versão certa?

Imagine que o setor de compras encontra estes arquivos em uma pasta:

procedimento-compras.txt
procedimento-compras-novo.txt
procedimento-compras-final.txt
procedimento-compras-final-certo.txt
procedimento-compras-agora-vai.txt

Qual contém a regra atual? Quem alterou? Quando? O que mudou? E se uma regra correta tiver sido substituída por engano?

Pense como profissional de Administração

  1. Que risco existe quando ninguém sabe qual documento está vigente?
  2. Que problema isso pode causar em compras e aprovações?
  3. Renomear arquivos como “final” e “final-certo” resolve o problema?
O problema é administrativo: regras mudam, documentos mudam e a organização precisa saber qual versão está válida e como chegou até ela.
2

Mas o ERP já não controla isso?

O processo operacional e o documento que descreve suas regras não são exatamente a mesma coisa.

O que um ERP pode controlar

Um ERP pode registrar requisições, aprovações, pedidos, fornecedores, estoque, financeiro, usuários, datas e histórico de operações. Dependendo do sistema, também pode oferecer fluxo de aprovação e recursos de auditoria.

E os procedimentos da organização?

A empresa também pode manter documentos que explicam como o trabalho deve ser realizado: procedimentos, instruções, normas e manuais. Esses documentos passam por revisões quando as regras mudam.

Processo de compras→Regra muda→Procedimento é revisado→Nova versão
Aqui, o Git será usado para controlar versões de um documento. Em uma organização real, ERP, gestão documental, BPM ou outra plataforma corporativa podem oferecer controles próprios de histórico, aprovação e acesso.
3

Prepare o computador

Você precisa apenas instalar o Git e reconhecer a janela em que os comandos serão digitados.

1. Instale o Git no Windows

Abra a página oficial do Git para Windows:

Abrir instalação oficial do Git →

Baixe o instalador para Windows e conclua a instalação. Para esta atividade, mantenha as opções padrão do instalador.

2. Conheça o Prompt de Comando

O Prompt de Comando é uma janela do Windows em que instruções de texto podem ser digitadas.

Abra o menu Iniciar, digite cmd e abra Prompt de Comando.

Você verá algo parecido com:

C:\Users\Aluno>

O texto antes de > indica a pasta atual. O cursor depois de > é o lugar onde você digita.

Daqui em diante, os blocos pretos representam comandos ou informações vistas no Prompt de Comando.

3. Verifique a instalação

Digite:

git --version

Se aparecer algo começando com git version, o Git está instalado. Se o Prompt já estava aberto antes da instalação, feche a janela, abra novamente e repita o comando.

Checkpoint: apareceu uma versão do Git? Então o computador está pronto para continuar.
4

Crie o Procedimento de Solicitação de Compras

Antes de controlar versões, precisamos ter um documento administrativo para acompanhar.

1. Crie a pasta

No Explorador de Arquivos, crie uma pasta chamada procedimento-compras em um local fácil de encontrar, como Documentos.

2. Crie o arquivo

Abra o Bloco de Notas e digite:

PROCEDIMENTO DE SOLICITAÇÃO DE COMPRAS

Objetivo
Organizar as solicitações de compras da empresa.

1. O funcionário identifica a necessidade de compra.
2. A solicitação é encaminhada ao responsável pelo setor.
3. O setor de compras consulta fornecedores.
4. A compra é aprovada pelo responsável.
5. O setor de compras realiza o pedido.
6. O material recebido é conferido.
7. A conclusão da compra é registrada.

Salve dentro da pasta criada com o nome:

procedimento-solicitacao-compras.txt
Checkpoint: abra novamente o arquivo. Se o procedimento aparecer completo, continue.
5

Guarde a primeira versão

O procedimento está pronto. Agora vamos registrar seu estado atual antes de qualquer mudança.

Abra o Prompt de Comando na pasta correta

No Explorador de Arquivos, abra a pasta procedimento-compras. Clique na barra de endereço, digite cmd e pressione Enter.

A janela deverá mostrar um caminho terminado em algo parecido com:

...\procedimento-compras>

Isso confirma que os próximos comandos serão executados dentro da pasta do procedimento.

Comece o histórico

Digite um comando por vez:

git init

Esse comando inicia o controle de versões na pasta.

Agora identifique os registros desta atividade. Essa configuração valerá somente para esta pasta:

git config user.name "SEU NOME"
git config user.email "aluno@example.com"

Para esta atividade, não é necessário usar seu e-mail pessoal.

Veja a situação da pasta:

git status

Procure o nome procedimento-solicitacao-compras.txt entre os arquivos ainda não registrados.

Prepare o arquivo para entrar na primeira versão:

git add .

Confira novamente:

git status

Agora o arquivo deverá aparecer entre as alterações preparadas para registro.

Registre a primeira versão:

git commit -m "Cria procedimento inicial de compras"
Checkpoint: o commit foi criado? Então a primeira versão do procedimento está registrada.
6

Uma regra de compras mudou

Uma nova decisão administrativa exige a revisão do procedimento.

Nova política

A empresa decidiu que o setor de compras deve obter três cotações antes de realizar a compra.

Atualize o documento

No Bloco de Notas, troque a etapa 3 por:

3. O setor de compras obtém três cotações de fornecedores.

Salve o arquivo.

No Prompt de Comando, digite:

git status

O Git deverá indicar que procedimento-solicitacao-compras.txt foi modificado.

Checkpoint: o Git detectou a mudança, mas ela ainda não foi registrada como uma nova versão.
7

Confira e registre a mudança

Antes de criar uma nova versão, veja exatamente o que foi alterado.

Veja a diferença

Digite:

git diff

Procure a linha antiga sobre consulta de fornecedores e a nova linha com as três cotações.

Por que isso é útil?

Você não precisa comparar dois documentos inteiros manualmente. O Git mostra quais linhas foram retiradas e quais foram acrescentadas.

Registre a nova versão

git add .
git commit -m "Exige tres cotacoes antes da compra"
Checkpoint: primeiro você conferiu a alteração; depois registrou a nova versão.
8

Uma segunda regra mudou

Repita o mesmo processo para consolidar o controle de versões.

Nova regra de aprovação

Compras acima de R$ 5.000 passam a exigir aprovação da gerência.

Atualize o procedimento

Depois da etapa das três cotações, inclua:

4. Compras acima de R$ 5.000 precisam de aprovação da gerência.

Renumerar as etapas seguintes faz parte da revisão do documento. Salve o arquivo.

Confira a diferença:

git diff

Se a nova regra estiver correta, registre:

git add .
git commit -m "Inclui aprovacao da gerencia acima de 5000 reais"
Checkpoint: o procedimento já possui três versões registradas: a inicial e duas revisões administrativas.
9

Consulte o histórico

Agora o conjunto de versões permite reconstruir como o procedimento evoluiu.

Digite:

git log

Observe a identificação do autor configurado, a data, o identificador do commit e a mensagem de cada registro.

Para uma visão mais curta:

git log --oneline

Você deverá encontrar os registros da versão inicial, das três cotações e da aprovação acima de R$ 5.000.

Rastreabilidade: o histórico permite verificar a ordem das mudanças e recuperar versões anteriores. Em ambientes corporativos, identidade, autorização e aprovação formal dependem também dos controles da organização.
10

Uma regra foi alterada por engano

Agora o histórico será usado para recuperar uma informação correta sem apagar o que aconteceu.

Simule um erro

Troque R$ 5.000 por R$ 50.000, salve e registre essa alteração:

git add .
git commit -m "Altera limite de aprovacao"

Encontre a versão correta

git log --oneline

Localize o registro imediatamente anterior ao erro e copie seu identificador.

Substitua IDENTIFICADOR pelo código encontrado:

git restore --source=IDENTIFICADOR procedimento-solicitacao-compras.txt

Abra o arquivo e confirme que o valor voltou para R$ 5.000.

Antes de registrar a correção, confira:

git diff

Se a alteração estiver correta, registre:

git add .
git commit -m "Corrige limite de aprovacao para 5000 reais"
Checkpoint: o erro continua no histórico e a correção também. A sequência dos acontecimentos permanece rastreável.
11

Leve o histórico para o GitHub

Até aqui tudo ficou no computador. Agora o mesmo histórico poderá ser consultado online.

Git e GitHub não são a mesma coisa

Git controla as versões na pasta do computador. GitHub é um serviço online onde um repositório Git pode ser armazenado e compartilhado.

1. Crie o repositório

Entre no GitHub. Se ainda não tiver conta, crie uma conta gratuita e conclua a confirmação solicitada pelo próprio serviço.

Escolha New repository e use o nome procedimento-compras. Como o conteúdo desta atividade é fictício, o repositório pode ser público. Não adicione README, licença ou outros arquivos iniciais.

2. Conecte a pasta ao GitHub

Copie a URL HTTPS exibida pelo GitHub. No Prompt de Comando, execute um comando por vez:

git branch -M main
git remote add origin COLE_A_URL_AQUI
git push -u origin main

Na primeira publicação, o Git pode abrir uma janela ou o navegador para autenticação. Conclua o acesso pelo método oferecido pelo Git/GitHub. Não digite sua senha do GitHub no Prompt de Comando.

3. Confira no navegador

Atualize a página do repositório. O arquivo deverá aparecer. Abra o histórico de commits e compare com os registros vistos no computador.

Segurança: esta atividade usa um documento fictício. Não publique procedimentos reais, dados internos, senhas ou informações confidenciais em um repositório público.
12

Onde esse recurso se encaixa na Administração

Controle de versões é útil, mas não substitui os demais controles de uma organização.

RecursoAjuda principalmente a
ERPIntegrar operações e informações de áreas como compras, estoque e financeiro.
GitRegistrar, comparar e recuperar versões de arquivos.
GitHubArmazenar e compartilhar online um repositório Git.
Gestão documental / BPMControlar documentos e fluxos com regras próprias de aprovação, acesso, vigência e processo.
Não confunda: Git e GitHub não substituem ERP, aprovação formal, controle de acesso, assinatura, política de documentos ou sistemas corporativos próprios para essas funções.
13

Agora é com você

Aplique o mesmo processo a uma nova decisão administrativa.

Nova regra

A empresa decidiu que toda solicitação aprovada deve ser concluída em até dois dias úteis após a aprovação.

  1. Decida onde essa regra deve entrar no procedimento.
  2. Faça a alteração e salve o arquivo.
  3. Use git diff para conferir a mudança.
  4. Use git add . e crie um commit com uma mensagem clara.
  5. Use git push para enviar a nova versão ao GitHub.
  6. Localize no histórico o registro correspondente à mudança.

Checkpoint final

  1. Por que nomes como “final” e “final-certo” são frágeis?
  2. Qual é a diferença entre conferir uma mudança e registrar uma versão?
  3. Como o histórico ajuda a rastrear alterações?
  4. Por que uma correção também deve ficar registrada?
  5. Em quais outros documentos administrativos esse método poderia ser útil?
Leve para a Administração: controlar versões significa saber o que mudou, quando mudou e como recuperar um estado anterior. O Git tornou essas mudanças visíveis durante a atividade.
