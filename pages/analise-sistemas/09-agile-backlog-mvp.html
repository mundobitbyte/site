Etapa 9

Transformando análise em pequenas entregas

Já sabemos bastante sobre o sistema. Agora precisamos decidir o que aprender e entregar primeiro, sem confundir agilidade com ausência de análise.

Do modelo para a entrega

Requisitos, Casos de Uso e modelos não desaparecem. Eles fornecem contexto para organizar o trabalho em partes menores. A pergunta muda de “o que existe no sistema?” para “qual fatia coerente entregamos primeiro?”.

Por que dividir o trabalho?

Imagine tentar construir de uma vez cadastro, ordens, diagnóstico, orçamento, pagamento, mensagens, relatórios e inteligência artificial. O projeto demoraria muito para produzir algo utilizável, e poderíamos descobrir tarde que uma decisão estava errada.

Nova necessidade

Precisamos organizar o trabalho em partes que tenham valor e permitam aprender cedo. Para isso aparecem nomes como Épico, Feature, User Story, Backlog e MVP. Vamos abrir cada um antes de usá-lo.

Não confunda

“Cliente consulta a situação” expressa valor para o usuário. “Criar campo no banco” é trabalho técnico. Os dois podem ser necessários, mas não representam a mesma coisa.

User Story — História de Usuário

O formato ajuda a preservar três perguntas: quem precisa, o que precisa e por quê.

Como [papel], quero [capacidade], para [valor]

Como atendente, quero localizar rapidamente uma ordem, para responder ao cliente sem consultar várias fontes.

A frase não substitui conversa, regras ou critérios. Ela funciona como um lembrete curto do valor que estamos tentando entregar.

3 Cs: por que três letras C?

É uma forma de lembrar três palavras em inglês que começam com C e ajudam a não tratar a História de Usuário como uma frase isolada:

  • Card — cartão: o registro curto da necessidade;
  • Conversation — conversa: o diálogo que esclarece contexto, regra e dúvida;
  • Confirmation — confirmação: os critérios usados para verificar se o comportamento esperado foi atendido.

Backlog: o que é?

Backlog é uma palavra inglesa usada para uma lista de trabalho ainda a realizar. No desenvolvimento de produto, o Product Backlog — Backlog do Produto — é uma lista ordenada das necessidades que podem entrar no produto.

“Ordenada” é importante: não é apenas um depósito de ideias. Os itens mais importantes ou mais necessários para aprender costumam ficar mais acima.

PrioridadeItemPor que agora?
1Abrir ordemSem ordem, o fluxo não começa.
2Registrar diagnósticoBase para orçamento.
3Gerar e registrar decisão do orçamentoLibera ou impede reparo.
4Atualizar situação da ordemResolve o problema central de acompanhamento.
5Consulta do clienteEntrega valor visível e reduz chamadas.

Priorizar não é escolher o que parece mais interessante

Para decidir a ordem, podemos considerar:

  • valor para o usuário;
  • risco;
  • dependência — algo que precisa existir antes de outro item;
  • urgência;
  • aprendizado necessário;
  • custo aproximado.

Chegamos à pergunta que cria o MVP

Temos muitas necessidades no backlog, mas ainda não queremos construir tudo de uma vez. Então surge a pergunta:

Qual é a menor versão que já resolve o problema principal e permite aprender com uso real?

É para responder a essa pergunta que usamos o conceito de MVP.

MVP — Minimum Viable Product — Produto Mínimo Viável

MVP é a sigla de Minimum Viable Product, em português Produto Mínimo Viável. É a menor versão coerente do produto que já entrega valor suficiente para ser usada ou validada e gerar aprendizado.

Mínimo não significa malfeito

MVP não é “qualquer coisa incompleta”. A versão pode ter menos funções, mas o que ela entrega precisa funcionar com a qualidade e a segurança necessárias para seu contexto.

Construindo o recorte da Conecta

Comece pelo problema central: acompanhar uma Ordem de Serviço do início até uma situação consultável. Para isso, precisamos preservar uma cadeia mínima:

Cliente/equipamento→Ordem→Diagnóstico→Orçamento/decisão→Situação→Consulta

MVP possível

  • cliente/equipamento;
  • ordem;
  • diagnóstico;
  • orçamento/decisão;
  • situação;
  • consulta simples.

Pode ficar para depois

  • pagamento integrado;
  • notificações automáticas;
  • relatórios avançados;
  • IA de triagem.

Observe: segurança e integridade mínimas não viram “fase futura” só porque estamos fazendo MVP.

Story Map — Mapa de Histórias

Story Map significa Mapa de Histórias. Ele organiza as necessidades acompanhando a jornada do usuário. Isso ajuda a enxergar uma versão horizontal mínima do processo em vez de terminar um setor inteiro e deixar os outros sem funcionamento.

Aprofundamento: INVEST, Ready e Done

Aprofundamento Estes nomes aparecem muito em equipes ágeis, mas não precisam virar decoreba.

INVEST

INVEST reúne iniciais de palavras em inglês usadas para revisar uma História de Usuário:

  • I — Independent: independente quando possível;
  • N — Negotiable: negociável, não uma solução engessada;
  • V — Valuable: valiosa para alguém;
  • E — Estimable: compreensível o suficiente para estimar;
  • S — Small: pequena o suficiente;
  • T — Testable: testável.

Definition of Ready

Definição de “pronto para começar”: critérios que ajudam a verificar se existe informação suficiente para iniciar o trabalho.

Definition of Done

Definição de “concluído”: condições de qualidade e processo que precisam ser satisfeitas para considerar um item terminado.

Critério de aceitação ≠ Definition of Done

O critério de aceitação descreve o comportamento esperado de um item. A Definition of Done pode conter condições que valem para muitos itens, como revisão, teste e documentação necessária.

Conferência com as etapas anteriores

Uma História de Usuário sem requisito, evidência ou necessidade correspondente merece desconfiança. E um requisito prioritário que nunca aparece no backlog pode indicar que estamos deixando uma necessidade importante para trás.
