Etapa 4

Análise Estruturada: processos, dados e decisões

O fluxograma mostrou o caminho. Agora precisamos enxergar o sistema pela circulação das informações e representar decisões com mais precisão.

Voltando um nível

No AS-IS apareceu uma pergunta simples: “quem registra a aprovação?”. Se nosso levantamento não consegue responder de onde vem essa informação, voltamos à Etapa 2 e investigamos. Modelar também serve para revelar o que ainda não sabemos.

O que significa Análise Estruturada?

Análise Estruturada é uma forma clássica de estudar sistemas separando perguntas que costumam se misturar. Em vez de olhar apenas para telas, observamos processos — o que transforma informação —, dados — a informação que circula ou precisa permanecer — e decisões — condições que mudam o que acontece.

Por que precisamos disso agora?

O fluxograma respondeu “qual atividade vem depois?”. Mas ele não respondeu bem “que dado entrou?”, “quem forneceu?”, “onde ficou guardado?” e “que informação saiu?”. É essa nova dúvida que traz as ferramentas desta etapa.

Primeiro: a fronteira do sistema

Antes de abrir o sistema em várias partes, precisamos separar o que está dentro da solução e quem está fora, mas troca informação com ela. O Diagrama de Contexto mostra o sistema como um único bloco e as entidades externas ao redor.

Retângulo externo

Representa alguém ou algum serviço fora da fronteira que envia ou recebe informação.

Bloco central

Representa o sistema inteiro como uma caixa única. Ainda não mostramos seu interior.

Seta com nome

Mostra que informação atravessa a fronteira e em qual direção.

Construa primeiro uma troca simples

Imagine apenas: Cliente → dados do equipamento → Conecta. Esse pequeno trecho já diz quem está fora, qual informação entra e para onde ela vai. Agora podemos acrescentar outros participantes.

Leia o contexto antes de seguir

O Cliente, o Fornecedor e os serviços de Pagamento e Mensagens estão fora do bloco central porque não são partes internas da Conecta. Mesmo assim, trocam informações com ela. Essa é a ideia de fronteira.

DFD — Diagrama de Fluxo de Dados

DFD significa Diagrama de Fluxo de Dados. Ele muda a pergunta: em vez de acompanhar principalmente a ordem das atividades, acompanhamos os dados que entram, são transformados, saem e precisam ficar guardados.

Quatro elementos essenciais do DFD

1. Entidade externa

Origem ou destino externo dos dados. Costuma aparecer como retângulo. Ex.: Cliente.

2. Processo

Transforma dados de entrada em dados de saída. Aqui aparece como círculo. Ex.: Registrar atendimento.

3. Fluxo de dados

É a informação que circula. Aparece como seta com um nome. Ex.: “dados do equipamento”.

4. Depósito de dados

Representa informação que precisa permanecer disponível. Aqui aparece como retângulo identificado por D1, D2.... Ex.: D2 Ordens.

DFD não é banco de dados

O depósito indica apenas que a informação precisa ser conservada. Ainda não estamos escolhendo tabelas de banco de dados nem uma tecnologia específica de armazenamento.

Monte um pedaço antes do DFD inteiro

Vamos usar apenas três elementos:

Clientedados do equipamento →1. Registrar atendimentoordem aberta →D2 Ordens

Leia em voz alta: o Cliente fornece dados do equipamento; o processo Registrar atendimento usa esses dados; o resultado “ordem aberta” precisa permanecer no depósito de Ordens. Se você consegue contar essa história, já começou a ler um DFD.

DFD Nível 0 da Conecta

Nível 0 é uma visão ainda geral, mas já divide o sistema em seus principais processos. Não tente decorar o desenho: escolha uma entidade, siga uma seta, veja qual processo recebe o dado e para onde o resultado vai.

Leia comigo mais uma vez

Localize Cliente. Siga “dados do equipamento” até o processo 1. Registrar atendimento. Depois procure “ordem aberta”. A leitura é sempre origem → dado → processo → novo dado/destino.

Decomposição e balanceamento

Decompor significa abrir um processo grande em processos menores para entendê-lo melhor. Ex.: “Gerenciar orçamento” pode ser detalhado em gerar proposta, registrar decisão e atualizar situação.

Balanceamento significa manter coerência entre os níveis. Se no nível mais geral entra “diagnóstico” e sai “orçamento”, o detalhamento não pode fazer esses fluxos desaparecerem sem explicação.

Dicionário de Dados

Aqui, dicionário não significa lista de palavras comuns. É um registro do significado dos dados usados no projeto, para que todos entendam o mesmo nome da mesma maneira.

Quando o fluxo não basta: decisões

Considere três condições: está em garantia? cliente aprovou? peça está disponível? Um desenho com muitos losangos começa a ficar confuso. Precisamos de ferramentas específicas.

Árvore de Decisão

Organiza perguntas em sequência e abre ramos conforme cada resposta. É útil quando a ordem das perguntas importa.

Tabela de Decisão

Coloca condições e ações em linhas/colunas para conferir combinações. É útil quando queremos evitar uma combinação esquecida.

RegraGarantia?Aprovado?Peça disponível?Ação
R1Sim—SimProsseguir conforme garantia
R2NãoSimSimIniciar reparo
R3NãoSimNãoSolicitar peça
R4NãoNão—Encerrar sem reparo

Na tabela, R significa Regra: R1 é “Regra 1”, R2 é “Regra 2” e assim por diante. O símbolo “—” indica que aquela condição não importa para aquela regra específica.

Faça agora

  1. No Diagrama de Contexto, aponte o que está dentro da fronteira e cite duas entidades externas.
  2. No DFD pronto, identifique uma entidade externa, um processo, um fluxo de dados e um depósito e explique o que cada símbolo significa.
  3. Monte primeiro um fragmento com uma entidade → um processo → um depósito. Só depois amplie para um Diagrama de Contexto e, em seguida, para um DFD Nível 0.
  4. Escolha três nomes de dados que precisam de definição no dicionário.
  5. Crie uma tabela de decisão com pelo menos três condições e verifique se alguma combinação ficou sem resposta.
