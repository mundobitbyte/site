Etapa 7

O sistema visto pelos usuários

Os requisitos dizem o que precisa existir. Agora perguntamos: que objetivo cada ator pretende alcançar ao interagir com o sistema?

Da regra para o objetivo

RF03 diz que o sistema deve registrar diagnóstico. RN01 diz que reparo exige aprovação. Mas quem inicia essas interações? O que cada participante tenta conseguir? Essa mudança de ponto de vista nos leva aos Casos de Uso.

Ator é papel, não necessariamente pessoa

Um ator representa um papel que interage com o sistema.

  • Atendente;
  • Técnico;
  • Gerente;
  • Cliente;
  • Serviço de Pagamento, quando houver integração.

A mesma pessoa pode exercer mais de um papel; um ator também pode ser outro sistema.

Caso de Uso

Um Caso de Uso representa um objetivo observável do ator em relação ao sistema. Prefira nomes com verbo + objeto:

Bom

Abrir ordem
Registrar diagnóstico
Aprovar orçamento
Consultar andamento

Fraco

Tela de cadastro
Botão orçamento
Módulo técnico
Banco de clientes

Diagrama inicial

O diagrama oferece uma visão rápida de objetivos e fronteira. Ele não mostra a ordem temporal das ações — e não deve ser forçado a isso.

Descrição textual: onde o comportamento ganha detalhe

UC04 — Registrar decisão do orçamento

Objetivo: registrar se o cliente aprovou ou recusou a proposta.

Ator principal: Atendente.

Pré-condição: existir orçamento pendente.

Fluxo principal:

  1. Atendente localiza a ordem.
  2. Sistema apresenta orçamento pendente.
  3. Atendente informa aprovação.
  4. Sistema registra decisão, usuário e horário.
  5. Sistema altera situação da ordem.

Fluxo alternativo: cliente recusa; sistema registra recusa e impede início do reparo.

Pós-condição: decisão fica registrada e a ordem assume situação coerente.

Caso de Uso não é tela

“Abrir ordem” pode envolver uma ou várias telas. Uma mesma tela pode apoiar diferentes Casos de Uso. Manter essa separação evita projetar interface cedo demais.

include, extend e generalização

Esses relacionamentos existem e podem ser úteis, mas entram somente quando simplificam um modelo real. Não vamos transformar o diagrama em um exercício de símbolos.

Aprofundamento

<<include>> pode indicar comportamento reutilizado obrigatório; <<extend>> pode representar comportamento opcional sob condição; generalização pode organizar atores/casos relacionados. Use com parcimônia.

Conferência circular

Para cada Caso de Uso, procure seus requisitos e regras. Para cada requisito funcional importante, pergunte se existe algum objetivo de ator que o justifique. Nem todo requisito vira Caso de Uso, mas lacunas inesperadas merecem investigação.

Faça agora

  1. Identifique quatro atores da Conecta.
  2. Associe pelo menos oito objetivos relevantes.
  3. Escolha um Caso de Uso e escreva fluxo principal, alternativo e exceção.
  4. Relacione o Caso de Uso a pelo menos dois requisitos e uma regra de negócio.

O que ainda falta?

Sabemos o objetivo do usuário, mas alguns Casos de Uso ainda possuem comportamento interno complexo. Em outros pontos precisamos compreender conceitos do domínio e estados da ordem.

Nova lacuna

Precisamos escolher, entre os diagramas UML, apenas os que respondem às perguntas que surgiram: fluxo, interação, conceitos e estados.
