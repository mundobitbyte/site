Etapa 5

Como saber se um arquivo foi alterado?

Controlar quem entra é importante. Mas, quando um arquivo circula entre pessoas e máquinas, ainda precisamos responder outra pergunta: o conteúdo continua exatamente igual?

O contrato parece igual. Isso não prova que seja igual.

Imagine que a Conecta Serviços envie um contrato e receba uma cópia de volta. Visualmente, tudo parece normal. Só que um valor foi alterado de R$ 5.000,00 para R$ 5.001,00.

Em documentos grandes, mudanças pequenas podem passar despercebidas. Precisamos de uma forma de gerar uma evidência comparável a partir do conteúdo do arquivo.

Uma impressão digital do conteúdo

Uma função de hash recebe dados como entrada e produz um valor de tamanho definido. Nesta prática usaremos SHA-256 — Secure Hash Algorithm 256-bit.

O hash não serve para “abrir” o arquivo e não é uma versão criptografada do texto. Ele serve muito bem para uma pergunta específica: o conteúdo digital comparado permaneceu igual?

Antes do laboratório, fixe a lógica

Mesmo arquivo + mesmo algoritmo → esperamos o mesmo hash. Conteúdo alterado → esperamos outro hash. O hash funciona aqui como evidência de integridade.

Faça você mesmo no PowerShell

  1. Crie uma pasta chamada seguranca-mbb.
  2. Dentro dela, crie um arquivo de texto chamado contrato.txt com duas linhas: Cliente: Alfa e Valor: R$ 5.000,00. Verifique se o Windows não o salvou como contrato.txt.txt.
  3. Abra a pasta no Explorador de Arquivos do Windows.
  4. Clique na barra de endereços, digite powershell e pressione Enter. O PowerShell abrirá já posicionado nessa pasta.
  5. Execute:
Get-FileHash .\contrato.txt -Algorithm SHA256

Anote o valor exibido na coluna Hash.

  1. Abra novamente contrato.txt.
  2. Troque apenas R$ 5.000,00 por R$ 5.001,00.
  3. Salve o arquivo.
  4. Execute novamente o mesmo comando.
  5. Compare os dois hashes. Eles devem diferir após a alteração. Se o comando não encontrar o arquivo, confira o nome e a pasta.

O que o resultado permite afirmar?

Se os hashes forem diferentes, os conteúdos digitais comparados não são idênticos. Se forem iguais usando o mesmo algoritmo, temos forte evidência de que o conteúdo comparado é igual, embora colisões de hash sejam teoricamente possíveis.

Mas repare no limite: hash igual não prova que o arquivo seja legítimo, seguro ou autorizado. Se alguém alterar um arquivo e depois lhe entregar apenas a versão alterada, você ainda precisa de uma referência confiável para comparação.

Integridade não é autenticidade

“O arquivo não mudou desde a referência que possuo” é diferente de “sei quem produziu este arquivo e confio na origem”. Essa diferença voltará quando falarmos de certificados e assinaturas digitais.

E senhas? É só aplicar SHA-256?

Não. Armazenamento de senha tem necessidades próprias. Sistemas modernos usam mecanismos específicos como Argon2id, bcrypt, scrypt ou PBKDF2, normalmente com um valor aleatório chamado salt. O laboratório desta etapa é sobre integridade de arquivo, não sobre implementar autenticação.

O hash percebe mudança, mas não esconde o conteúdo

Se alguém copiar contrato.txt, o hash pode ajudar a verificar se houve alteração. Porém ele não impede ninguém de abrir e ler o arquivo. Essa limitação cria a próxima necessidade.

Próxima necessidade: confidencialidade

Como fazer para que uma pessoa que obtenha a cópia do arquivo não consiga compreender o conteúdo sem possuir a chave adequada?
