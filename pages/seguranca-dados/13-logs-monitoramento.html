Etapa 13

Como descobrir o que aconteceu?

Defesa em profundidade reduz riscos, mas não elimina incidentes. Quando algo estranho acontece, precisamos trocar “acho que foi” por evidências registradas.

O problema aconteceu de madrugada. Ninguém estava olhando.

Às 8h, a equipe percebe que houve acesso incomum durante a noite. Sem registros, sobra especulação: quem entrou? de onde? o que executou? em que horário? quanto tempo permaneceu?

Sistemas conseguem registrar eventos mesmo quando nenhuma pessoa está acompanhando a tela. Esses registros são os logs.

Quatro palavras parecidas, quatro funções diferentes

Log é o registro de um evento. Logging é o processo de produzir esses registros. Monitoramento acompanha o ambiente ao longo do tempo. Alerta chama atenção quando uma condição exige análise ou ação.

Exemplo rápido

O sistema registra cinco tentativas de login: isso é log. Uma ferramenta acompanha continuamente essas tentativas: isso é monitoramento. Ao detectar vinte falhas em um minuto e avisar a equipe: isso é alerta.

Sem horário confiável, eventos não formam uma história

Imagine que o firewall registre 02:14 e o servidor registre 02:19 para o mesmo evento porque os relógios estão desalinhados. Reconstruir a sequência fica mais difícil.

Por isso, sincronização de tempo importa. E os próprios logs também precisam de proteção: se o mesmo usuário investigado puder apagar ou alterar facilmente os registros, parte do valor como evidência se perde.

Prática orientada — observe consultas no MySQL

Use somente um MySQL de laboratório

O general query log pode registrar grande volume de informações, incluir conteúdo presente nas consultas e produzir impacto operacional. Não ative esse recurso em produção para esta atividade.

Roteiro pronto

Baixar mysql-general-log-lab.sql →

A conta usada no laboratório precisa ter permissão para alterar variáveis globais. Se você não tiver esse ambiente, acompanhe o roteiro como demonstração orientada.

Observe a relação ação → registro

  1. Confira se o general_log está ligado ou desligado.
  2. Defina temporariamente a saída como tabela para facilitar a observação.
  3. Ative o general_log.
  4. Execute duas consultas de teste conhecidas.
  5. Consulte registros recentes na tabela mysql.general_log.
  6. Relacione horário, usuário, tipo de comando e consulta registrada.
  7. Desative o general query log.
  8. Confirme que ele realmente ficou desligado.

Os comandos do laboratório

SHOW VARIABLES LIKE 'general_log';
SHOW VARIABLES LIKE 'log_output';

SET GLOBAL log_output = 'TABLE';
SET GLOBAL general_log = 'ON';

SELECT NOW();
SELECT 'Mundo bit Byte' AS origem;

SELECT event_time, user_host, command_type, argument
FROM mysql.general_log
ORDER BY event_time DESC
LIMIT 20;

SET GLOBAL general_log = 'OFF';
SHOW VARIABLES LIKE 'general_log';

O objetivo não é decorar esses comandos. É enxergar a relação entre uma ação executada e o registro que permite investigá-la depois.

Registrar tudo também pode ser um problema

Mais log não significa automaticamente mais segurança. Volume excessivo, dados sensíveis nos registros e falta de revisão podem transformar logging em custo sem benefício. Registramos o que ajuda a operar, detectar e investigar.

Quando a evidência aponta um incidente, observar não basta

Logs podem mostrar que algo aconteceu. A equipe então precisa decidir como conter o problema sem destruir justamente os registros necessários para entendê-lo.

Próxima necessidade: responder com método

O que fazemos primeiro quando encontramos um incidente — bloquear tudo imediatamente ou preservar evidências? A resposta exige equilíbrio.
