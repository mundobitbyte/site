Etapa 9

Quando aquilo que digitamos vira parte de um comando

Até agora protegemos arquivos, conexões e acesso. Agora vamos olhar para uma falha criada pela própria aplicação quando ela confunde aquilo que o usuário digitou com a estrutura de uma instrução SQL.

O campo pede um nome. O programa espera receber apenas um nome.

Na Conecta Serviços, uma tela de busca deveria receber algo simples, como Ana. O programa precisa usar esse valor para procurar clientes no banco.

Uma consulta normal poderia ser:

SELECT * FROM clientes WHERE nome = 'Ana';

Aqui existem duas coisas diferentes: a estrutura do comando e o valor procurado.

O problema começa quando o programa mistura essas duas coisas

nome = input("Digite o nome: ")
sql = "SELECT * FROM clientes WHERE nome = '" + nome + "'"

Esse código concatena diretamente o texto recebido com o comando SQL. Enquanto a entrada for apenas Ana, tudo parece funcionar. Mas o programa está confiando que o usuário sempre entregará um valor inocente.

Se a entrada conseguir modificar a estrutura interpretada pelo banco, temos uma classe de vulnerabilidade chamada SQL Injection, ou injeção de SQL.

A ideia que vale mais do que decorar um ataque

Entrada externa é dado. Dado não deve ganhar o poder de reescrever a estrutura do comando.

Veja acontecer em um ambiente seguro

O laboratório usa sqlite3, que acompanha instalações comuns do Python. Você precisa ter o Python 3 disponível no computador; se o comando de versão falhar, prepare o ambiente antes de seguir. Ele cria um banco temporário no próprio computador e coloca lado a lado uma consulta vulnerável e uma consulta parametrizada.

Baixe o laboratório

Baixar sql-injection-local.py →

Use somente este arquivo didático. Não teste entradas de injeção em sistemas de terceiros ou sem autorização.

  1. Crie uma pasta chamada sql-injection-mbb e coloque nela o arquivo baixado.
  2. Abra a pasta no Explorador de Arquivos, clique na barra de endereços, digite powershell e pressione Enter.
  3. Confirme que o Python está disponível:
python --version

Se o Windows usar o lançador py, teste py --version.

  1. Execute python .\sql-injection-local.py ou py .\sql-injection-local.py.
  2. Pesquise primeiro por Ana. As duas versões devem localizar apenas Ana. Esse é o resultado de referência para entrada normal.
  3. Depois use, somente nesse laboratório local, a entrada indicada pelo próprio programa: ' OR 1=1 --.
  4. Compare os resultados: na versão vulnerável, a entrada de teste pode fazer aparecer os três clientes; na parametrizada, nenhum cliente deve ter aquele nome literal. Se o resultado diferir, não avance sem conferir a entrada digitada e a execução.
  5. Digite SAIR para encerrar.

O que mudou na versão segura?

Na versão vulnerável, o programa monta a instrução unindo pedaços de texto. Na versão parametrizada, comando e valor seguem caminhos separados.

cursor.execute(
    "SELECT * FROM clientes WHERE nome = ?",
    (nome,)
)

O ? não é a lição principal. Outras linguagens e bibliotecas usam sintaxes diferentes. O conceito é que a aplicação entrega a estrutura do comando separadamente dos valores.

Validação de entrada ajuda, mas não substitui parametrização

Verificar formato, tamanho e tipo de entrada é útil por vários motivos. Mas a defesa central contra SQL Injection continua sendo não construir SQL por concatenação de dados externos.

Mesmo um sistema bem programado ainda pode perder dados

Eliminar SQL Injection não elimina falha de disco, exclusão acidental, corrupção, ransomware ou erro humano. Segurança também precisa responder ao momento em que a prevenção falha.

Próxima necessidade: recuperação

Se os dados desaparecerem hoje, a empresa consegue restaurá-los de maneira comprovada — ou apenas espera que o backup funcione?
