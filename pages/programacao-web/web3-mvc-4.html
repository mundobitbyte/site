Web III — Em desenvolvimento.

O prazo já permanece no banco. Se criássemos agora um formulário sem proteção, qualquer visitante que descobrisse o endereço poderia trocar o aviso da cozinha. Esconder um link não resolveria: o servidor precisa reconhecer quem está fazendo a alteração.

Você já encontrou esse problema no painel do Web II. Aqui vamos reencontrar a distinção essencial: autenticação verifica a identidade; autorização verifica se essa identidade pode realizar uma ação. Entrar não transforma automaticamente uma pessoa em operadora.

Primeiro observe a recusa

Com os arquivos desta etapa acrescentados à sua aplicação, abra http://localhost:8000/operador/atendimento em uma janela privativa. O endereço deve levar à entrada, sem mostrar o formulário de edição. A consulta pública em /api/atendimento precisa continuar funcionando sem login. A proteção se aplica à escrita, não obriga o cliente do Café a criar uma conta.

A rota de edição usa dois filtros, chamados middlewares: auth exige uma sessão; can:alterar-atendimento consulta a permissão definida para o papel de operador.

Conferir app/Providers/AppServiceProvider.php

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

<?php
namespace App\Providers;
use App\Models\User;
use Illuminate\Support\Facades\Gate;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function register(): void {}
    public function boot(): void
    {
        Gate::define('alterar-atendimento', fn (User $usuario) => $usuario->papel === 'operador');
    }
}

O model de usuário preserva a senha como hash. O comando abaixo cria uma identidade fictícia somente na aplicação local. Não use a senha de sua conta pessoal nem a do Meu MbB:

php artisan cafe:operador operador@example.test

Execute na raiz, depois da migration da etapa anterior. O terminal pedirá uma senha local de pelo menos 12 caracteres e não a imprimirá. Guarde-a para o exercício. O comando recusa um usuário já existente, em vez de trocar sua senha silenciosamente. As credenciais não fazem parte do checkpoint.

Uma entrada confirmada pelo servidor

Acrescente o controller de sessão, o model de usuário e a página de entrada do download. A tentativa de entrada consulta o usuário e a senha no servidor; não basta o navegador guardar autenticado: true. Quando a sessão é confirmada, seu identificador é renovado.

Conferir app/Http/Controllers/SessaoController.php

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

<?php
namespace App\Http\Controllers;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Auth;
use Illuminate\Validation\ValidationException;

class SessaoController
{
    public function entrar(Request $pedido)
    {
        $dados = $pedido->validate(['email'=>['required','email'],'password'=>['required','string']]);
        if (!Auth::attempt($dados)) throw ValidationException::withMessages(['email'=>'E-mail ou senha inválidos.']);
        $pedido->session()->regenerate();
        return redirect()->intended(route('operador.atendimento'));
    }
    public function sair(Request $pedido)
    {
        Auth::logout(); $pedido->session()->invalidate(); $pedido->session()->regenerateToken();
        return redirect()->route('login');
    }
}

Valide antes de gravar

No formulário, deixe o prazo vazio e salve. Consulte o balcão: a mensagem deve orientar o visitante a procurar a equipe. Depois informe zero e consulte novamente. Ao encerrar os pedidos, não pode continuar aparecendo uma promessa de retirada em minutos.

Os atributos do HTML ajudam a preencher os campos, mas podem ser contornados. A classe de requisição também verifica nome, situação e prazo no servidor. nullable aceita ausência; integer exige inteiro; between:0,240 aplica a regra do exercício.

Conferir app/Http/Requests/AtualizarAtendimentoRequest.php

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

<?php
namespace App\Http\Requests;
use Illuminate\Foundation\Http\FormRequest;

class AtualizarAtendimentoRequest extends FormRequest
{
    public function authorize(): bool { return $this->user()?->can('alterar-atendimento') === true; }
    public function rules(): array
    {
        return ['nome' => ['required','string','max:100'], 'aberto' => ['required','boolean'],
            'minutos' => ['nullable','integer','min:0','max:240']];
    }
    public function messages(): array
    {
        return ['nome.required' => 'Informe o nome do Café.', 'minutos.integer' => 'Informe minutos inteiros.',
            'minutos.max' => 'O limite combinado para este formulário é 240 minutos.'];
    }
}

Encontre @csrf na view. O token associa o envio à sessão da aplicação e ajuda a recusar pedidos forjados a partir de outro site. CSRF não substitui autenticação, autorização ou validação; cada proteção responde a uma pergunta diferente.

Teste um valor negativo e um texto com mais de 100 caracteres para o nome. A aplicação deve recusar a alteração e orientar a correção. O dado anterior precisa permanecer. Depois use “Sair da edição” e tente voltar ao endereço protegido: uma página antiga aberta não é prova de que a sessão continua válida.

A equipe informa; o visitante consulta

Comprove acesso recusado sem sessão, alteração aceita para o operador, recusa de dado inválido e saída da conta. Execute composer test na raiz para repetir os testes automatizados disponíveis. Eles usam um banco de teste isolado; a execução não deve apagar seu banco do Café. Agora Marina consegue cuidar do aviso. Ela também quer atualizar o cardápio sem editar o JSON à mão.
