“Abri a pasta, mas o botão não respondeu.”

Uma colega vai conferir o balcão antes de usá-lo no atendimento. Você enviou os arquivos, ela abriu a página e o aviso apareceu, mas o botão continuou desabilitado. Na sua máquina funcionava. O que pode ter ficado para trás?

Na sua cópia, localize public/js/balcao/main.js. Compare com cliente-balcao/src/main.ts. Um é o código que o navegador carrega; o outro é a fonte que você edita. Se a nova pasta recebeu somente os .ts, ainda precisa gerar o JavaScript. Se recebeu apenas um .js antigo, pode parecer pronta sem representar as últimas correções.

Vamos conferir a entrega em uma pasta nova, sem depender das instalações ou dos arquivos gerados da primeira cópia. Você não vai refazer o Café nem estudar as seis aulas inteiras outra vez. Vai reunir as mudanças que já construiu, preparar o ambiente e demonstrar o resultado.

Separar o que construímos do que as ferramentas geram

Guarde sua solução atual. Crie uma pasta chamada conferencia-cap2 e extraia nela a referência final do Capítulo 1. Abra a pasta cafe-aurora-web3 extraída pelo VS Code. É uma cópia de conferência, sem suas mensagens ou credenciais pessoais.

Usaremos essa base já conhecida. A partir da sua solução concluída, copie somente os arquivos que evoluíram no capítulo, mantendo os caminhos:

Não copie node_modules, vendor, banco, credenciais nem public/js/balcao/main.js. As dependências e o JavaScript serão preparados nesta nova cópia. Se quiser demonstrar também suas alterações pessoais em outros arquivos, acrescente-as conscientemente depois da comparação; preserve a pasta original.

Antes de executar comandos, abra atendimento.ts e confira se há AbortController, conferência dos três campos e consulta ao endereço correto. Abra a API e confira se chama a função PHP. Não use o download final para substituir silenciosamente uma parte que ainda não consegue explicar.

Gerar o que o navegador realmente usa

No terminal da raiz de cafe-aurora-web3, confira o PHP e inicie o servidor. Se sua primeira cópia ainda ocupa a porta 8000, pare aquele servidor com Ctrl + C no terminal correspondente. Usaremos uma aplicação por vez nessa porta.

php --version
php -d opcache.enable=0 -S localhost:8000 -t public

Deixe esse terminal em execução. Abra outro terminal, confirme que ele está na raiz da nova aplicação e entre na pasta do cliente:

cd cliente-balcao
node --version
npm --version
npm ci
npm run build

Use a versão Node 24 já preparada na Aula 2. npm ci usa o package-lock para instalar uma cópia das dependências; não procura node_modules na solução anterior. O build verifica o TypeScript e gera public/js/balcao/main.js. Confira se o arquivo apareceu nesse caminho e se public/api, CSS e demais páginas continuam presentes.

Abra http://localhost:8000/balcao.php e clique em “Atualizar atendimento”. Confira também a resposta da API. O resultado deve vir da nova cópia, executada pelo terminal que você acabou de iniciar.

Se o build falhar, leia a primeira mensagem e confira o arquivo indicado; não entregue um .js de outra pasta para esconder o problema. Se o botão continuar desabilitado, abra o Console e a Rede: main.js foi encontrado? O script aponta para js/balcao/main.js? Os cinco ids ainda correspondem ao main.ts?

Se o PHP não for reconhecido no terminal do VS Code, retome a orientação de Laragon da Aula 1 com o professor. O caminho de configuração foi fundamentado na documentação; sua execução em Windows/Laragon ainda precisa ser conferida no laboratório.

Preparar o banco e o painel nesta cópia nova

O ZIP não inclui banco ou credenciais. Na raiz da nova aplicação, em um terminal livre, use a preparação já ensinada:

php src/verificar-ambiente.php
php src/inicializar-banco.php
php src/criar-administrador.php

O último comando pede usuário e senha locais. Confira PHP 8.5 e as extensões exigidas pela prática do Capítulo 1, incluindo PDO/SQLite. Não copie o banco pessoal para completar o ensaio. Se for repetir a suíte do Web II, instale as dependências com composer install e rode composer test, conforme a aula de testes.

Ao terminar, restaure “Café Aurora”, true, 30 e a API correta, sem atrasos ou falhas artificiais. Faça uma consulta válida na nova cópia e confira as duas páginas PHP.

Sua explicação acompanha os arquivos

Se houver um colega disponível, peça que ele prepare a cópia usando suas orientações. Observe onde precisa ajudá-lo: essa dificuldade pode revelar um caminho, comando ou arquivo que faltou explicar. Quando trabalhar sozinho, faça a conferência na pasta nova e registre as mesmas evidências; não declare um teste com outra pessoa que não aconteceu.

Depois explique individualmente, apontando para seus arquivos:

  1. Onde a regra do atendimento é preparada uma única vez e quem a consulta.
  2. Por que nomeNegocio, mensagemStatus e mensagemTempo são três textos, e onde cada um aparece.
  3. Como Promise/await, unknown e a conferência participam de momentos diferentes.
  4. O que acontece com a tela, o botão e a possibilidade de recuperação durante uma falha.
  5. Qual alteração precisa de build e qual precisa somente de uma nova consulta PHP.
  6. Como outra cópia produz o mesmo comportamento sem carregar suas dependências, dados ou credenciais.

Na avaliação, demonstre esses comportamentos, explique uma decisão e recupere um erro. Se houver uma lacuna, retome somente a experiência correspondente e confira de novo. Visitar a aula ou marcar um conteúdo como concluído não substitui a prática.

Use o Meu MbB para registrar sua própria evidência ou uma dúvida no conteúdo em que ela surgiu. Favoritos, anotações e retomada continuam seguindo os recursos do site; não é necessário criar um cadastro diferente para este capítulo.

Conferir a referência final do Capítulo 2

O código da aplicação é o mesmo que concluímos na Aula 6. Nesta aula, a conquista é reproduzir, verificar e explicar. O download não inclui dependências instaladas, JavaScript gerado, banco nem credenciais; siga a preparação acima para executá-lo.

A informação mudou uma vez. O balcão aprendeu a buscá-la.

No início, a página aberta conservava o aviso antigo. Agora ela consulta o servidor, confere os três campos e atualiza somente o atendimento. A mesma regra PHP continua servindo às duas telas, com uma orientação quando não há prazo e um caminho de recuperação quando a consulta falha.

Ao rever o Café, pense: se outra interface passar a usar essa informação, o que ela poderá reaproveitar e qual responsabilidade deverá continuar no servidor? Guarde sua explicação junto da entrega.
