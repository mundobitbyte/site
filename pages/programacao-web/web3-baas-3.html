A regra fica no serviço

Web III — Em desenvolvimento.

A identidade do operador foi reconhecida. Falta estabelecer a regra de acesso: visitantes podem consultar o aviso; o operador pode alterar uma configuração válida; ninguém deve apagar o atendimento por uma chamada comum do cliente.

Esconder o formulário não basta. Um programa pode chamar o serviço diretamente. As regras de segurança precisam ser verificadas pelo serviço para cada operação.

Leia a regra como uma pergunta do Café

Em firestore.rules, encontre o documento atendimento/atual. request.auth representa a identidade autenticada; a claim operador precisa ser verdadeira para criar ou atualizar. A leitura é pública porque o aviso se destina aos clientes.

Conferir firestore.rules

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function operador() { return request.auth != null && request.auth.token.operador == true; }
    function atendimentoValido() {
      let d = request.resource.data;
      return d.keys().hasAll(['nomeNegocio', 'pedidosAbertos', 'tempoEstimado'])
        && d.keys().hasOnly(['nomeNegocio', 'pedidosAbertos', 'tempoEstimado'])
        && d.nomeNegocio is string && d.nomeNegocio.size() >= 1 && d.nomeNegocio.size() <= 100
        && d.nomeNegocio.matches('.*[^ ].*') && d.pedidosAbertos is bool
        && (d.tempoEstimado == null || (d.tempoEstimado is int && d.tempoEstimado >= 0 && d.tempoEstimado <= 240));
    }
    match /atendimento/atual {
      allow read: if true;
      allow create, update: if operador() && atendimentoValido();
      allow delete: if false;
    }
    match /{document=**} { allow read, write: if false; }
  }
}

Permissão não é a única condição. O conjunto de campos precisa ser exatamente o combinado; nome não pode estar vazio; situação precisa ser booleana; minutos devem ser inteiro entre zero e 240 ou null. A checagem no TypeScript ajuda a orientar, mas a regra impede que um cliente diferente ignore essa validação.

Prove a recusa antes de abrir a edição

Acrescente os testes desta etapa. Pare os emuladores interativos com Ctrl+C para liberar as portas. Na raiz, execute npm test. O comando inicia emuladores de teste, usa identidades controladas e encerra os serviços no final.

Conferir tests/permissoes.test.mjs

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

import { before,after,test } from 'node:test';
import { readFile } from 'node:fs/promises';
import { initializeTestEnvironment,assertSucceeds,assertFails } from '@firebase/rules-unit-testing';
import { doc,setDoc,getDoc,deleteDoc } from 'firebase/firestore';
let ambiente;
const dados={nomeNegocio:'Café Aurora',pedidosAbertos:true,tempoEstimado:30};
before(async()=>{ambiente=await initializeTestEnvironment({projectId:'demo-cafe-aurora-web3',firestore:{rules:await readFile('firestore.rules','utf8')}});await ambiente.withSecurityRulesDisabled(c=>setDoc(doc(c.firestore(),'atendimento/atual'),dados));});
after(async()=>{await ambiente?.cleanup();});
test('visitante consulta, mas não escreve; identidade sem papel não autoriza',async()=>{
 const anon=ambiente.unauthenticatedContext().firestore();const leitor=ambiente.authenticatedContext('leitor',{operador:false}).firestore();
 await assertSucceeds(getDoc(doc(anon,'atendimento/atual')));
 for(const b of [anon,leitor])await assertFails(setDoc(doc(b,'atendimento/atual'),dados));
});
test('operador grava somente contrato válido e não apaga atendimento',async()=>{
 const b=ambiente.authenticatedContext('operador',{operador:true}).firestore();const r=doc(b,'atendimento/atual');
 for(const prazo of [null,0,240])await assertSucceeds(setDoc(r,{...dados,tempoEstimado:prazo}));
 for(const prazo of [-1,241,'30'])await assertFails(setDoc(r,{...dados,tempoEstimado:prazo}));
 await assertFails(setDoc(r,{...dados,nomeNegocio:'   '}));await assertFails(setDoc(r,{...dados,segredo:'extra'}));await assertFails(deleteDoc(r));
 await assertFails(getDoc(doc(b,'historico/qualquer')));
});

Observe os testes de visitante, leitor e operador. Mensagens PERMISSION_DENIED podem aparecer justamente nas operações que devem ser recusadas. O resultado importante é a verificação do teste: uma recusa esperada não é um teste falhando.

A suíte não usa sua conta pessoal nem altera um projeto real. Ela verifica regras carregadas no ambiente local; não demonstra que regras idênticas já foram publicadas na nuvem.

Retome a bancada de uso

Depois dos testes, execute novamente npm run retomar para importar a bancada guardada. Se ela não existia, siga o início e o preparo da primeira etapa. Confira que a consulta continua disponível. Não edite uma regra para allow read, write: if true apenas para fazer um erro desaparecer: isso removeria a condição que estamos tentando comprovar.

Consegue explicar uma operação recusada?

Mostre que visitante e leitor não escrevem, operador grava apenas valores válidos e exclusão não é permitida. Explique onde a verificação acontece. Agora podemos acrescentar um formulário que respeite essas condições e espere confirmação real da gravação.
