Os arquivos não levam os serviços junto

Café Aurora · cerca de 6 horas-aula de estudo, prática e verificação

Web III — Em desenvolvimento.

Uma colega recebeu a pasta e conseguiu abrir o HTML, mas não recebeu o atendimento. Os arquivos da página chegaram até ela; os serviços estavam em outro computador. Hospedar arquivos e disponibilizar os dados são partes diferentes da entrega.

Vamos preparar uma cópia limpa e identificar o ambiente antes de pensar em nuvem. A prática obrigatória continua local e não exige cadastro de faturamento.

Reproduza o que a colega precisa receber

Extraia a referência em outra pasta. Com Node 22 e Java 21, execute npm ci na raiz e em cliente-balcao. Faça o build do cliente. Encerre os emuladores da pasta anterior antes de iniciar npm run emuladores na nova e executar npm run preparar.

Abra http://localhost:5000, consulte, entre e altere um prazo. O emulador Hosting serve os arquivos de public; Auth, Firestore e Storage atendem os demais endereços configurados. Essa execução não publica o Café na internet.

O build produz arquivos em public/js/balcao e preserva o restante de public. Ele não transforma PHP em JavaScript. O formulário de mensagens anterior continua na aplicação PHP preservada; seu link de exercício usa localhost:8000 e depende daquele servidor em execução.

Configuração pública não é credencial de administração

O exemplo abaixo mostra quais dados públicos mudariam em um aplicativo registrado em um projeto real. Ele não é uma configuração pronta para usar: os marcadores precisam ser substituídos em um ambiente aprovado pelo professor. Nesta prática, mantenha src/ambiente.ts no modo local.

Conferir cliente-balcao/configuracao-nuvem.exemplo.ts.txt

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

// Somente depois de escolher um projeto de exercício autorizado e conferir as regras, custos e origem HTTPS.
// Substitua src/ambiente.ts pelos dados públicos do aplicativo Web registrado nesse projeto.
// Estes valores não são uma credencial Admin; nunca coloque chave privada ou conta de serviço no cliente.
export const modo: "local" | "nuvem" = "nuvem";
export const configuracao = {
  apiKey: "COPIAR_DA_CONFIGURACAO_PUBLICA_DO_APP",
  authDomain: "PROJETO_DE_EXERCICIO.firebaseapp.com",
  projectId: "PROJETO_DE_EXERCICIO",
  storageBucket: "COPIAR_O_BUCKET_REAL"
};
export const chaveVapid = "COPIAR_CHAVE_PUBLICA_WEB_PUSH";

Uma configuração pública identifica o projeto e seus serviços. A proteção dos dados continua nas regras e permissões. Uma chave privada de conta de serviço ou uma credencial Admin pertence ao servidor e nunca deve ser colada no cliente nem publicada no repositório.

Confira as condições antes de escolher nuvem

Storage em nuvem exige plano Blaze com faturamento vinculado. A implantação de Functions também depende desse plano. Faixas sem cobrança de uso não significam ausência de conta de faturamento ou garantia de custo zero.

Por isso não há comando de contratação ou deploy obrigatório nesta aula. Se a escola disponibilizar um ambiente real, sua configuração, permissões, custos e testes precisam ser combinados e verificados separadamente. Sem esse ambiente, registre “nuvem não executada” e conclua a reprodução local.
