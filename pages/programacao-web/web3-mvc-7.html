Web III · Servidor com Laravel

O Café cabe na rotina do celular

Web III — Em desenvolvimento.

Uma cliente abre o Café pelo celular para consultar a retirada e enviar o cardápio a outra pessoa. O site já se adapta à tela menor. Podemos aproveitar o compartilhamento do aparelho sem transformar essa possibilidade em uma obrigação para todos os navegadores.

Vamos acrescentar uma página pequena de atendimento móvel. Ela reutiliza a API que já existe. Não vamos criar outro prazo nem um cadastro exclusivo para celular.

Preparar os arquivos desta etapa

Baixar a referência da etapa 7. Ela contém a aplicação ao final desta etapa; não é uma nova tarefa nem uma substituição automática da sua solução.

Continue na sua pasta de trabalho que concluiu a etapa 6 deste percurso. A raiz é o lugar onde aparecem public e cliente-balcao. Não crie uma pasta cafe-aurora-web3 dentro dessa raiz.

  1. Salve os arquivos e pare o servidor antes de copiar dados. Preserve uma cópia da pasta atual.
  2. Extraia o download em uma pasta de referência separada. Abra o LEIA-ME-ETAPA.md que está dentro de cafe-aurora-web3.
  3. Compare os caminhos listados abaixo com sua pasta de trabalho. Acrescente os arquivos de apoio que ainda não existem. Para um arquivo já existente, compare a alteração antes de aplicá-la: não apague uma mudança sua sem entender a diferença. Os arquivos discutidos na aula são os que vamos construir e compreender.

Preserve dados, credenciais locais, .env e as dependências já instaladas. Uma pasta ausente no ZIP não é uma instrução para apagar sua cópia. A aula informa quando executar Composer, npm, migration ou build; copiar arquivos não executa esses preparos.

Conferir public/js/mobile.js

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

const consultar = document.querySelector("#consultar");
const retorno = document.querySelector("#retorno");
consultar.addEventListener("click", async () => {
  consultar.disabled = true;
  retorno.textContent = "Consultando…";
  try {
    const resposta = await fetch("/api/atendimento", { signal: AbortSignal.timeout(8000) });
    const dados = await resposta.json();
    if (!resposta.ok || !dados || ["nomeNegocio", "mensagemStatus", "mensagemTempo"].some(c => typeof dados[c] !== "string")) throw new Error();
    retorno.textContent = `${dados.nomeNegocio}. ${dados.mensagemStatus} ${dados.mensagemTempo}`;
  } catch { retorno.textContent = "Não foi possível confirmar o atendimento. Tente novamente."; }
  finally { consultar.disabled = false; consultar.focus(); }
});
document.querySelector("#compartilhar").addEventListener("click", async () => {
  const texto = document.querySelector("#compartilhamento");
  const url = new URL("cardapio.php", location.href).href;
  if (!navigator.share) { texto.textContent = "Este navegador não oferece compartilhamento nativo. Use o link abaixo."; return; }
  try { await navigator.share({ title: "Café Aurora", url }); texto.textContent = "Solicitação de compartilhamento concluída. Isso não comprova leitura pelo destinatário."; }
  catch (e) { texto.textContent = e.name === "AbortError" ? "Compartilhamento cancelado." : "Compartilhamento indisponível. Use o link abaixo."; }
});

A página tem um retorno textual para informar consulta, falha e conclusão. O botão fica indisponível durante a espera e volta a funcionar depois. Não há razão para manter o cliente preso em “Consultando…” quando a conexão falha.

Um recurso que depende do navegador

navigator.share faz parte da Web Share API: permite solicitar ao navegador o compartilhamento de um título e endereço. Não escolhemos nem controlamos o aplicativo que receberá o pedido. A pessoa continua decidindo se quer compartilhar e com quem.

O código confere se o recurso existe antes de usá-lo. Quando não existe, a página mantém um link que pode ser aberto e copiado. A recusa de permissão, a falta de suporte e o cancelamento não devem impedir o uso normal do cardápio.

Experimente o botão no navegador disponível. Se a janela de compartilhamento abrir, cancele uma vez e observe a orientação. Se não abrir, use o link alternativo. Não é necessário enviar uma mensagem real a alguém para concluir o exercício.

Recursos desse tipo dependem de suporte e contexto seguro, geralmente HTTPS; localhost recebe tratamento especial para desenvolvimento. Abrir pelo celular o IP de outro computador em HTTP não oferece automaticamente as mesmas condições. Não troque uma falha de ambiente por uma informação falsa de que o código compartilhou.

Funciona também sem o recurso extra?

Verifique consulta bem-sucedida, falha de consulta, ausência de compartilhamento nativo e link alternativo. Use teclado e ampliação de texto; o controle precisa continuar compreensível. Registre qual navegador usou e se o compartilhamento abriu ou ficou indisponível. Nosso próximo consumidor será outro programa, que pede um contrato XML em vez da resposta JSON do balcão.
