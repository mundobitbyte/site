Quando a consulta demora ou falha

Café Aurora · cerca de 2 horas-aula · 14 horas-aula previstas no capítulo

Web III — Em desenvolvimento.

O prazo sumiu. E agora?

O balcão já consegue pedir um aviso novo. Vamos conferir se a equipe também consegue continuar quando a consulta falha. Faça este ensaio somente na sua cópia local, mantendo a aba do balcão aberta.

No terminal do servidor PHP, pressione Ctrl + C. Sem recarregar o balcão, clique em “Atualizar atendimento”. A orientação deve mudar para “Não foi possível consultar. Tente novamente.”. O prazo antigo deve sair da tela, e o botão deve voltar a ficar disponível.

Reinicie o servidor na raiz de cafe-aurora-web3:

php -d opcache.enable=0 -S localhost:8000 -t public

Volte à mesma aba e consulte de novo. Os três textos retornaram? Você acabou de conferir a recuperação sem reinstalar ferramentas, refazer o build ou reconstruir a página. Se recarregasse a página com o PHP desligado, não haveria documento para o nosso botão executar; por isso mantivemos a aba aberta.

Não podemos deixar a pessoa esperando sem fim

Um servidor desligado costuma produzir uma falha rapidamente. Já uma conexão que continua aberta sem devolver dados pode manter o botão ocupado por muito tempo. Precisamos limitar a espera da consulta.

Vamos adotar 8 segundos, escritos como 8000 milissegundos, para este exercício. Esse número é uma escolha didática para conseguirmos observar o cancelamento. Não veio da cozinha, não altera os 30 minutos de preparo e precisaria ser avaliado com os usuários e a rede em um produto real.

AbortController cria um controle de cancelamento. Entregamos seu signal ao fetch; chamar abort() interrompe a espera do cliente. setTimeout agenda essa chamada para depois de 8000 ms e devolve um identificador. Guardamos esse identificador em temporizador para poder cancelar o agendamento.

O finally desta função tem outro trabalho: executar clearTimeout, tanto se os dados chegarem quanto se ocorrer um erro. Assim uma consulta concluída não deixa seu temporizador pendente. O finally do main.ts continua responsável por liberar o botão.

Em cliente-balcao/src/atendimento.ts, mantenha interface e conferirAtendimento. Troque somente obterAtendimento pela função a seguir. A consulta e suas conferências agora ficam dentro do try:

export async function obterAtendimento(): Promise<Atendimento> {
  const controlador = new AbortController();
  const temporizador = setTimeout(() => controlador.abort(), 8000);
  try {
    const resposta = await fetch("api/atendimento.php", {
      cache: "no-store",
      signal: controlador.signal,
    });
    if (!resposta.ok) {
      throw new Error(`A consulta respondeu HTTP ${resposta.status}.`);
    }
    const tipo = resposta.headers.get("Content-Type");
    if (tipo === null || tipo.split(";")[0].trim().toLowerCase() !== "application/json") {
      throw new Error("A resposta não foi identificada como JSON.");
    }
    const dados: unknown = await resposta.json();
    return conferirAtendimento(dados);
  } finally {
    clearTimeout(temporizador);
  }
}
Comparar o atendimento.ts completo

O contrato de três campos e a validação permanecem como na Aula 4.

export interface Atendimento {
  nomeNegocio: string;
  mensagemStatus: string;
  mensagemTempo: string;
}

export function conferirAtendimento(dados: unknown): Atendimento {
  if (typeof dados !== "object" || dados === null || Array.isArray(dados)) {
    throw new Error("A resposta precisa ser um objeto.");
  }
  if (!("nomeNegocio" in dados) || typeof dados.nomeNegocio !== "string" || dados.nomeNegocio.trim() === "") {
    throw new Error("Nome do negócio ausente ou inválido.");
  }
  if (!("mensagemStatus" in dados) || typeof dados.mensagemStatus !== "string" || dados.mensagemStatus.trim() === "") {
    throw new Error("Mensagem de situação ausente ou inválida.");
  }
  if (!("mensagemTempo" in dados) || typeof dados.mensagemTempo !== "string" || dados.mensagemTempo.trim() === "") {
    throw new Error("Mensagem de prazo ausente ou inválida.");
  }
  return {
    nomeNegocio: dados.nomeNegocio,
    mensagemStatus: dados.mensagemStatus,
    mensagemTempo: dados.mensagemTempo,
  };
}

Salve, faça npm run build em cliente-balcao e recarregue o balcão uma vez. Consulte normalmente antes de provocar a demora. Não alteramos main.ts nem o HTML nesta aula.

Agora abra public/api/atendimento.php. Dentro do try, imediatamente antes do require_once, acrescente temporariamente sleep(10);. sleep faz o PHP esperar dez segundos. Salve, mantenha o balcão aberto e clique. Observe “Consultando…”, o botão desabilitado e a retirada do prazo anterior. Por volta de oito segundos, a consulta deve falhar e liberar nova tentativa.

No Console, procure o erro de cancelamento, normalmente chamado AbortError. Na Rede, a requisição pode aparecer como cancelada. O navegador não ordenou que o PHP parasse seu trabalho: limitou a própria espera. O servidor de desenvolvimento pode continuar ocupado até terminar os dez segundos.

Retire sleep(10), salve e tente novamente depois desse ensaio terminar. A consulta deve se recuperar. Uma demora artificial não fica na API de referência, e nenhuma alteração PHP exige build.

Receber alguma coisa ainda não basta

Vamos testar separadamente as conferências que já escrevemos. Guarde uma cópia do conteúdo correto de public/api/atendimento.php fora de public, por exemplo em uma pasta ensaios na raiz. Em cada experiência abaixo, troque temporariamente o conteúdo do endpoint, salve e clique no balcão. Depois restaure a API correta e confirme uma consulta válida antes do próximo caso.

Comece com uma resposta que declara falha HTTP. Use este arquivo temporário:

<?php
http_response_code(500);
header("Content-Type: application/json; charset=utf-8");
echo '{"erro":"Falha controlada no ensaio."}';

O Console deve registrar HTTP 500. Repita substituindo apenas 500 por 404. Em ambos, resposta.ok impede tratar o corpo como Atendimento. Não basta renomear um arquivo para prometer um 404: dependendo da configuração, o servidor pode devolver outra página.

Ensaiar HTML no lugar de JSON

Mesmo com status 200, este tipo de conteúdo é recusado antes da leitura dos campos:

<?php
header("Content-Type: text/html; charset=utf-8");
echo '<p>Esta resposta não é o aviso JSON.</p>';
Ensaiar um JSON que não pode ser lido

O cabeçalho está correto, mas a chave aberta não forma um JSON completo. A leitura com resposta.json deve falhar:

<?php
header("Content-Type: application/json; charset=utf-8");
echo '{incompleto';
Ensaiar um campo ausente no JSON

É um JSON legível. Falta mensagemTempo, então conferirAtendimento deve recusá-lo:

<?php
header("Content-Type: application/json; charset=utf-8");
echo json_encode([
    "nomeNegocio" => "Café Aurora",
    "mensagemStatus" => "Pedidos para retirada estão abertos."
], JSON_UNESCAPED_UNICODE);

Em cada falha, confira três evidências: nenhuma situação ou estimativa antiga fica apresentada como atual; a orientação é compreensível; o botão permite tentar novamente. O Console ajuda quem desenvolve a distinguir os motivos, sem expor detalhes internos ao visitante.

Ao terminar, restaure a API completa da Aula 1 e consulte com sucesso. Não deixe sleep, arquivos de falha ou cópias de código privado em public.

A cozinha respondeu: ainda não há uma estimativa

Imagine uma situação diferente: o Café está recebendo pedidos, mas a equipe precisa conferir a fila antes de informar o prazo. A consulta funcionou; falta uma estimativa da cozinha. Seria incorreto escrever “0 minutos” ou anunciar falha de conexão.

Em src/atendimento.php, troque temporariamente 30 por null, salve e consulte. Na versão anterior pode aparecer “Tempo estimado: minutos.”. Encontramos uma limitação da regra PHP, não da rede ou do contrato de três textos.

Vamos retomar a ordem de condições praticada no TypeScript Essencial. Primeiro perguntamos se os pedidos estão encerrados. Só se estiverem abertos verificamos se o prazo é null; por último usamos o número. === null compara com ausência explicitamente: o número zero continua sendo um valor, não uma informação ausente.

Preserve seus valores do Café e altere o if/else de src/atendimento.php para a sequência deste arquivo. O sinal ! nega pedidosAbertos, e elseif significa “senão, se”:

<?php
function obterAtendimento(): array
{
    $nomeNegocio = "Café Aurora";
    $pedidosAbertos = true;
    $tempoEstimado = 30;

    if (!$pedidosAbertos) {
        $mensagemStatus = "Pedidos para retirada estão encerrados.";
        $mensagemTempo = "Consulte novamente durante o horário de atendimento.";
    } elseif ($tempoEstimado === null) {
        $mensagemStatus = "Pedidos para retirada estão abertos.";
        $mensagemTempo = "Consulte a equipe para saber o prazo de retirada.";
    } else {
        $mensagemStatus = "Pedidos para retirada estão abertos.";
        $mensagemTempo = "Tempo estimado: $tempoEstimado minutos.";
    }

    return [
        "nomeNegocio" => $nomeNegocio,
        "mensagemStatus" => $mensagemStatus,
        "mensagemTempo" => $mensagemTempo
    ];
}

Na referência completa, true e 30 já estão restaurados. Se preferir manter null enquanto faz a experiência, use a nova sequência de condições e só restaure 30 ao terminar. A função continua devolvendo os mesmos três campos; a API e o TypeScript não precisam conhecer a fila da cozinha.

Sem recarregar o balcão, faça uma combinação por vez, salve o PHP e consulte. Registre a frase recebida em cada caso:

Ausência, zero e encerramento têm significados diferentes
Pedidos / prazo no PHPResultado a conferir
true / 30Abertos, com 30 minutos.
false / 30Encerrados; consultar durante o horário de atendimento.
true / nullAbertos; consultar a equipe sobre o prazo.
false / nullEncerrados; a primeira condição continua prevalecendo.
true / 0Abertos, com o valor numérico 0. Ele não virou ausência.

O zero serve para conferir a comparação; não é uma promessa de preparo instantâneo. Restaure true e 30 e confirme a consulta. As duas páginas PHP também recebem a nova regra quando são solicitadas novamente.

Texto recebido continua sendo texto

A conferência verifica a presença e o tipo dos campos. Quem apresenta também tem uma responsabilidade: usar textContent, como já fizemos, para que uma frase não seja interpretada como HTML. Não troque por innerHTML para “resolver” a apresentação.

Faça um ensaio curto no nome do negócio em src/atendimento.php: use "<strong>Café Aurora</strong>". Salve e consulte. As marcas devem aparecer como texto, sem transformar o nome em HTML. Reponha “Café Aurora”. No HTML inicial, htmlspecialchars continua protegendo a saída PHP.

Confira ainda a raiz do servidor: o comando termina em -t public. src, cliente-balcao e eventuais dados privados ficam fora dela. O endpoint público entrega somente a resposta necessária; uma falha interna recebe a mensagem genérica já preparada na Aula 1.

Provocar, explicar e recuperar

Escolha uma falha de consulta, mostre a retirada da estimativa antiga e recupere o atendimento. Explique a diferença entre os oito segundos de espera e os minutos de preparo. Demonstre depois o caso aberto/null como resposta válida e justifique por que encerrado/null segue a primeira condição.

Conferir os arquivos ao fim da Aula 6

A referência não contém falhas artificiais e termina com pedidos abertos e 30 minutos. Compare em outra pasta, preservando sua solução, seus dados e as experiências guardadas fora de public.
