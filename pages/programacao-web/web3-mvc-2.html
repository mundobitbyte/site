As mesmas telas, outra organização

Web III — Em desenvolvimento.

O objeto reuniu as regras do aviso. Se Marina mudar o prazo, as duas telas continuam concordando. Agora ela pede uma área de edição. Antes de abrir esse novo caminho, precisamos conseguir responder: quem recebe o pedido do navegador, quem procura a informação e quem monta a página?

Vamos organizar primeiro uma consulta que já funciona. O resultado desta etapa será pequeno e visível: abrir o atendimento pelo Laravel, mudar uma parte da apresentação e perceber que a resposta do balcão continua igual. As mensagens, o cardápio e as imagens do Café permanecem no projeto.

Preparar os arquivos desta etapa

Baixar a referência da etapa 2. Ela contém a aplicação ao final desta etapa; não é uma nova tarefa nem uma substituição automática da sua solução.

Continue na sua pasta de trabalho que concluiu a etapa 1 deste percurso. A raiz é o lugar onde aparecem public e cliente-balcao. Não crie uma pasta cafe-aurora-web3 dentro dessa raiz.

  1. Salve os arquivos e pare o servidor antes de copiar dados. Preserve uma cópia da pasta atual.
  2. Extraia o download em uma pasta de referência separada. Abra o LEIA-ME-ETAPA.md que está dentro de cafe-aurora-web3.
  3. Compare os caminhos listados abaixo com sua pasta de trabalho. Acrescente os arquivos de apoio que ainda não existem. Para um arquivo já existente, compare a alteração antes de aplicá-la: não apague uma mudança sua sem entender a diferença. Os arquivos discutidos na aula são os que vamos construir e compreender.

Preserve dados, credenciais locais, .env e as dependências já instaladas. Uma pasta ausente no ZIP não é uma instrução para apagar sua cópia. A aula informa quando executar Composer, npm, migration ou build; copiar arquivos não executa esses preparos.

Prepare o ambiente sem substituir seu projeto

Laravel é um framework PHP: fornece uma estrutura de trabalho e recursos para receber requisições, organizar regras e produzir respostas. Você continua escrevendo PHP no VS Code. O Laragon reúne as ferramentas do ambiente local no Windows; o Composer, que já apareceu nos testes do Web II, instala as bibliotecas descritas pelo projeto.

Vamos usar PHP 8.5 e Laravel 13. O kit já traz a estrutura de apoio adaptada ao Café; você não precisa criar outra aplicação vazia para depois refazer as páginas.

Como conferir o PHP do Laragon e do VS Code?
  1. Abra o Laragon. Em Menu → PHP → Version, selecione a instalação 8.5. Se ela não estiver disponível, consulte Menu → Tools → Quick add e as instruções oficiais para acrescentar uma versão. Confira a versão realmente instalada; a presença do Laragon não garante um número específico de PHP.
  2. Abra o Terminal do Laragon. No VS Code, confira também o terminal em que executará os comandos abaixo. No Windows, where.exe php mostra os executáveis encontrados. Se o primeiro resultado ou a versão diferir, use o terminal do Laragon preparado para o exercício e abra ali a pasta do Café. A documentação do Laragon explica como disponibilizar suas ferramentas no PATH; depois de mudar esse ajuste, feche e reabra os terminais.
  3. Execute php --ini. Edite somente o php.ini indicado como carregado por essa instalação. Em php -m, confira PDO, pdo_sqlite, mbstring, OpenSSL, XML/DOM e as extensões exigidas pelo Composer. SOAP será conferido antes da integração XML. Se precisar habilitar uma extensão já fornecida com o PHP, retire o ponto e vírgula da linha correspondente e confira novamente; não copie DLLs de outra instalação.

Se o VS Code ainda apontar para o antigo C:/php/php.exe na configuração php.validate.executablePath, ajuste para o executável que escolheu no Laragon. A validação do editor e o PHP do terminal precisam apontar para a instalação pretendida.

Na política consultada em 28/10/2026, o Laragon permite uso não comercial sem licença paga, com lembrete de licença e sem atualização automática. Utilize a instalação da escola ou a modalidade permitida para esta prática.

php -v
php --ini
php -m
composer --version

A versão do PHP deve começar com 8.5 e o Composer precisa responder com sua versão. Se ele ainda não estiver disponível, retome somente a preparação de Composer no Web II. Não é necessário refazer o módulo. Se a instalação apontar falta de extensão ou incompatibilidade, corrija o ambiente indicado pela mensagem antes de avançar.

Abra “Preparar os arquivos desta etapa”, acima, para incorporar o apoio do download à sua cópia. As pastas novas app, bootstrap, config, resources e routes, além de artisan e dos arquivos Composer, organizam a aplicação. Preserve dados, as mensagens e suas credenciais.

Na raiz, copie .env.example para .env pelo explorador do VS Code, somente se ainda não existir. Esse arquivo guarda a configuração local. Para este kit, a conexão é SQLite e o caminho padrão aponta para o banco do Café em dados; não precisamos ligar MySQL no Laragon para esta experiência. Execute:

composer install --no-interaction --no-plugins
php artisan key:generate

install segue as versões do composer.lock e cria vendor com as bibliotecas. artisan é a entrada dos comandos do Laravel. key:generate prepara a chave local na primeira configuração; não execute esse preparo outra vez a cada aula. A sessão e o cache desta etapa usam arquivos locais.

Abra pelo servidor certo

Encerre o servidor PHP anterior com Ctrl+C. Na raiz que contém artisan, inicie:

php artisan serve --host=localhost --port=8000

Deixe esse terminal aberto e visite http://localhost:8000/atendimento. Você deve encontrar Café Aurora, a situação dos pedidos e o prazo que deixou na etapa anterior. Abra também /balcao.php. Se veio de uma cópia limpa do download, execute npm ci e npm run build em cliente-balcao, em outro terminal, antes de conferir o balcão. O endereço no navegador continua sendo o do PHP.

Se a porta estiver ocupada, procure o terminal do servidor anterior. Se aparecer “Could not open input file: artisan”, confira a pasta atual: o comando foi executado fora da raiz. Uma mensagem de chave ausente pede conferir o .env e o preparo inicial. Esses problemas de ambiente não se resolvem alterando a regra do prazo.

Mude a página e observe o que permaneceu

No VS Code, abra resources/views/atendimento.blade.php. Localize o título e acrescente um texto depois do nome, mantendo as chaves que já estão nele:

<h1>{{ $dados['nomeNegocio'] }} · consulta da cozinha</h1>

Salve e recarregue /atendimento. O complemento deve aparecer no título. Agora abra /api/atendimento: continuam sendo os três campos conhecidos, sem esse complemento. Você mudou a apresentação de uma página, não o nome salvo nem a informação que o balcão consulta. Retire o complemento depois da experiência. Alteramos uma view PHP; não há novo build de TypeScript para essa mudança.

Uma requisição, três responsabilidades

Com a tela funcionando, percorra seu caminho uma vez:

  1. O navegador pede /atendimento. Em routes/web.php, Route::get associa esse endereço a uma ação.
  2. A ação é mostrar, no AtendimentoController. Ela chama a função conhecida e entrega o resultado com o nome dados para a view.
  3. A view atendimento.blade.php usa esses dados para montar o HTML que acabou de ver. O navegador recebe o resultado, não as instruções Blade.
Conferir routes/web.php

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

<?php
use Illuminate\Support\Facades\Route;
Route::get('/',fn()=>view('inicio-legado'));
Route::get('/atendimento',[\App\Http\Controllers\AtendimentoController::class,'mostrar']);
Route::get('/api/atendimento',[\App\Http\Controllers\AtendimentoController::class,'publico']);
Route::get('/api/atendimento.php',[\App\Http\Controllers\AtendimentoController::class,'publico']);
Conferir app/Http/Controllers/AtendimentoController.php

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

<?php
namespace App\Http\Controllers;
class AtendimentoController {
 public function mostrar(){require_once base_path('src/atendimento.php');return view('atendimento',['dados'=>obterAtendimento()]);}
 public function publico(){require_once base_path('src/atendimento.php');return response()->json(obterAtendimento())->header('Cache-Control','no-store');}
}

Leia a rota como “quando receber uma consulta GET neste endereço, use este controller e chame este método”. ::class fornece o nome da classe; 'mostrar' indica a ação. Já namespace organiza o nome completo da classe, como um endereço dentro do código. O Composer faz o carregamento automático a partir da configuração App\ → app/; você não precisa escrever um require para cada controller.

Esse arranjo conduz ao padrão MVC. Model representa dados e regras — nossa classe do aviso já participa dessa responsabilidade. View apresenta. Controller coordena a chegada da requisição e a resposta. Um model não é sinônimo de banco: na próxima etapa aprenderemos como ligar um registro persistente a essa organização.

Conferir resources/views/atendimento.blade.php

Caminho a partir da raiz da aplicação. Abra o arquivo no VS Code e compare com a explicação desta etapa.

@extends('layout')
@section('titulo','Atendimento')
@section('conteudo')
<h1>{{ $dados['nomeNegocio'] }}</h1><p>{{ $dados['mensagemStatus'] }}</p><p>{{ $dados['mensagemTempo'] }}</p>
@endsection

Blade é o sistema de templates do Laravel. @extends('layout') reaproveita o layout; @section preenche uma área dele. {{ $dados['nomeNegocio'] }} apresenta o valor com escape de HTML. Compare com o cuidado que já tivemos ao mostrar nomes vindos de dados externos.

O arquivo public/index.php passou a iniciar o Laravel. A página inicial anterior foi preservada em resources/views/inicio-legado.blade.php, e a rota / a apresenta. “Legado” significa o código que já existia. Abra o início e confira o caminho do cardápio antes de continuar.

Encontre os caminhos sem adivinhar arquivos

Em outro terminal na raiz, execute php artisan route:list --path=atendimento. Localize as rotas da página e da API. /api/atendimento.php também foi preservado para manter a consulta TypeScript existente. O endereço de uma resposta não precisa ter o mesmo nome de um arquivo físico.

Execute php artisan help make:controller. Esse apoio gera um esqueleto de controller quando precisamos de um novo; ele é chamado de scaffolding. Nosso controller já está preenchido, por isso agora basta conhecer a ajuda. Quando surgir a consulta de CEP, geraremos outro e completaremos sua ação.

O que deve continuar igual?

Mostre a página funcionando, repita a pequena mudança no título e explique por que ela não mudou o JSON. Confirme início, cardápio e balcão. A conquista não é decorar nomes de pastas: é conseguir seguir uma consulta entre rota, controller e view, preservando a regra do Café. Falta permitir que o prazo sobreviva sem ficar escrito na criação do objeto; essa será nossa próxima necessidade.
