IA e Programação

Professor Ronaldo Lavestein
Módulo 5 · IA e Programação

Você herdou um programa que funciona. Agora precisa fazê-lo evoluir sem perder o controle.

O laboratório de informática da escola empresta notebooks, kits Arduino e câmeras para aulas e projetos. Um aluno começou um pequeno programa em Python para registrar os empréstimos, mas deixou o curso antes de terminar. O código funciona para um caso simples — e agora ficou com você.

Durante este módulo, esse mesmo projeto receberá novos pedidos, apresentará erros, precisará guardar dados, ganhará testes e será preparado para outra pessoa continuar. A IA participará de todas essas etapas, mas com uma regra: ela ajuda a investigar e modificar; você continua responsável por compreender, decidir e comprovar.

Regra central

Se você não consegue explicar o que mudou, por que mudou e como comprovou que funciona, a tarefa ainda não terminou — mesmo que o código tenha sido escrito pela IA.

Antes de começar — este módulo não ensina Python do zero

Você não precisa ser especialista, mas precisa reconhecer o básico para que a IA não vire um atalho que esconde aquilo que você ainda não aprendeu.

  • Variáveis e entrada/saída com input e print.
  • Decisões com if, elif e else.
  • Funções simples com parâmetros e return.
  • Listas ou dicionários em situações básicas.
  • Executar um programa e localizar uma mensagem de erro.

Se isso ainda estiver novo demais

Volte primeiro para Programação de Computadores. Aqui vamos aprender a trabalhar com IA durante o desenvolvimento, não substituir os fundamentos da linguagem.

1. Segunda-feira — o projeto chega às suas mãos

O professor entrega um arquivo chamado app.py. Antes de pedir “melhore esse código”, você precisa descobrir o que já existe e o que realmente funciona.

equipamentos = {
    "NB01": {"nome": "Notebook 01", "disponivel": True},
    "CAM01": {"nome": "Câmera 01", "disponivel": True},
    "ARD01": {"nome": "Kit Arduino 01", "disponivel": True}
}


def emprestar(codigo):
    codigo = codigo.strip().upper()
    item = equipamentos.get(codigo)

    if item is None:
        return "Equipamento não encontrado."

    if not item["disponivel"]:
        return "Equipamento indisponível."

    item["disponivel"] = False
    return f'{item["nome"]} emprestado com sucesso.'


codigo = input("Código do equipamento: ")
print(emprestar(codigo))

Esse código é pequeno de propósito. O desafio não é impressionar com quantidade de linhas; é aprender a entrar em um projeto existente sem mandar a IA reconstruí-lo por conta própria.

Primeira tarefa

Execute o programa pelo menos três vezes: com NB01, com nb01 e com um código inexistente. Anote o que aconteceu antes de conversar com a IA.

2. Antes de modificar, faça a IA ajudá-lo a ler o que já existe

Você poderia perguntar “esse código está bom?”. Isso convida uma avaliação genérica. O que você precisa agora é construir um mapa do comportamento.

Ainda não altere o código. Explique este programa para alguém que conhece variáveis, if e funções, mas está aprendendo dicionários. Responda em quatro partes: 1. quais dados o programa guarda; 2. o que a função emprestar recebe; 3. quais decisões ela toma; 4. o que muda nos dados quando um empréstimo é aceito. Depois proponha três entradas para eu prever o resultado antes de executar.

O aluno continua trabalhando

Leia a explicação, mas volte ao código. Aponte com o dedo ou destaque onde cada afirmação da IA aparece. Se você não consegue localizar a evidência no programa, ainda não deve tratá-la como entendimento.

Primeira amarra

A IA não entrou para gerar código. Entrou para ajudá-lo a construir um modelo mental do programa que você herdou.

3. Terça-feira — chega o primeiro pedido real de mudança

O responsável pelo laboratório testa o protótipo e identifica duas limitações: o programa precisa registrar para quem o equipamento foi emprestado e também precisa permitir a devolução.

O impulso que queremos evitar

Adicione nome do aluno, devolução, menu e deixe tudo profissional.

Há vários requisitos misturados, nenhuma regra para casos problemáticos e liberdade demais para a IA redesenhar o projeto.

Transforme o pedido em comportamento

Não escreva código ainda. Para o programa atual, precisamos: - registrar o nome de quem recebe um equipamento; - impedir novo empréstimo enquanto ele estiver indisponível; - permitir devolução; - após devolver, o equipamento deve voltar a ficar disponível e deixar de ter responsável. Liste as alterações necessárias nos dados e nas funções. Depois proponha casos de teste. Preserve a estrutura atual sempre que possível.

Observe a diferença: agora a IA precisa raciocinar sobre regras verificáveis, não sobre a palavra vaga “melhorar”.

4. Antes do novo código, transforme as regras em testes que qualquer pessoa entenda

A equipe concorda que não deve aceitar uma mudança apenas porque “parece funcionar”. Antes de editar, você registra o comportamento esperado.

Por que isso vem antes?

Quando o esperado foi escrito antes da solução, fica mais difícil aceitar uma alteração só porque o código parece convincente.

5. A IA propõe uma alteração pequena — e você recebe a responsabilidade de revisá-la

Depois de aprovar o plano, a IA sugere acrescentar o campo emprestado_para e uma função de devolução. O trecho abaixo contém exatamente o tipo de situação que queremos aprender a revisar:

def emprestar(codigo, aluno):
    codigo = codigo.strip().upper()
    item = equipamentos.get(codigo)

    if item is None:
        return "Equipamento não encontrado."
    if not item["disponivel"]:
        return "Equipamento indisponível."

    item["disponivel"] = False
    item["emprestado_para"] = aluno
    return f'{item["nome"]} emprestado para {aluno}.'


def devolver(codigo):
    codigo = codigo.strip().upper()
    item = equipamentos.get(codigo)

    if item is None:
        return "Equipamento não encontrado."
    if item["disponivel"]:
        return "Este equipamento já está disponível."

    item["emprestado_para"] = None
    return f'{item["nome"]} devolvido com sucesso.'

Não procure o erro imediatamente. Use os casos definidos na etapa anterior. Empreste NB01, devolva e tente emprestar novamente.

O resultado surpreende

A função informa que a devolução foi concluída, mas o próximo empréstimo continua sendo recusado. Não há mensagem vermelha. O programa simplesmente mantém um estado incoerente.

6. Quarta-feira — o primeiro bug ensina que depurar não é pedir “arruma”

Agora existe uma evidência concreta: depois de devolver, o equipamento continua indisponível. Em vez de mandar a IA reescrever a função, você conduz uma investigação.

Não corrija ainda. Simule esta sequência usando o código atual: 1. emprestar("NB01", "Ana"); 2. devolver("NB01"); 3. emprestar("NB01", "Bruno"). Depois de cada etapa, mostre os valores de disponivel e emprestado_para de NB01. Identifique em qual etapa o estado deixa de representar a regra esperada.

Ao acompanhar o estado, fica evidente que devolver() remove o responsável, mas nunca devolve disponivel para True.

Agora proponha a menor correção possível. Não altere nomes, estrutura ou mensagens fora do necessário. Depois diga quais testes da tabela anterior precisam ser repetidos.

O ciclo de depuração

Reproduzir → observar → localizar evidência → formular hipótese → alterar pouco → repetir testes. A IA ajudou na investigação, não substituiu o raciocínio.

7. Quinta-feira — o programa funciona durante a aula e esquece tudo quando fecha

No fim do dia surge um problema mais real do que qualquer erro de sintaxe: os empréstimos existem apenas na memória. Ao fechar o programa, NB01 volta a aparecer disponível.

A equipe decide salvar o estado em um arquivo JSON. Antes de gerar código, você pede à IA que delimite a mudança:

O programa atual guarda equipamentos em um dicionário e perde as alterações ao encerrar. Quero persistir esse estado em dados/equipamentos.json usando apenas a biblioteca padrão do Python. Antes de escrever código, proponha: 1. quando os dados devem ser carregados; 2. quando devem ser salvos; 3. o que deve acontecer na primeira execução, quando o arquivo ainda não existe; 4. quais erros não devemos esconder silenciosamente.

Uma nova necessidade produz um novo conceito

Agora faz sentido falar de arquivo, serialização, primeira execução e tratamento de erro. Esses assuntos não aparecem porque estavam numa lista de conteúdos; aparecem porque o projeto precisa lembrar o que aconteceu.

8. A primeira tentativa de persistência falha — e a mensagem de erro vira parte da investigação

A primeira versão tenta abrir o arquivo assim que o programa inicia:

import json

ARQUIVO_DADOS = "dados/equipamentos.json"


def carregar_dados():
    with open(ARQUIVO_DADOS, "r", encoding="utf-8") as arquivo:
        return json.load(arquivo)

Na primeira execução, a pasta e o arquivo ainda não existem. O Python mostra algo parecido com:

FileNotFoundError: [Errno 2] No such file or directory:
'dados/equipamentos.json'

Pedido que esconde a evidência

Está dando erro no JSON. Conserta.

Pedido que permite investigar

Na primeira execução do projeto, carregar_dados() gera FileNotFoundError para dados/equipamentos.json. O comportamento desejado é: se ainda não houver arquivo, iniciar com os equipamentos padrão; se existir, carregar os dados salvos. Explique a causa antes de propor a menor alteração.

A solução também precisa garantir que a pasta exista antes de salvar. É aqui que documentação real entra no fluxo.

9. A IA sugere uma API que “parece Python” — mas o projeto não aceita fé em nomes convincentes

Durante a correção, uma resposta da IA sugere Path.makedirs() para criar a pasta. O nome parece plausível, mas o método correto de pathlib.Path para esse caso é mkdir().

Você sugeriu Path.makedirs(). Antes de alterar meu código, indique a classe e o método exatos que está assumindo, os parâmetros relevantes e o que devo confirmar na documentação oficial do Python. Se o método sugerido não existir, corrija a orientação sem inventar outro.

Programação tem uma fonte de verdade executável

Nome de método, assinatura, versão e comportamento precisam existir no ambiente real. Uma explicação muito segura não transforma uma API inexistente em API válida.

Para salvar com segurança, o projeto pode criar a pasta com algo como Path(ARQUIVO_DADOS).parent.mkdir(parents=True, exist_ok=True) antes de abrir o arquivo para escrita.

10. Na semana seguinte, outro aluno precisa testar o projeto — e o arquivo único começa a atrapalhar

O app.py agora lê teclado, altera dados, salva arquivo e contém todas as regras. Importar o arquivo para testar uma função também dispara o programa interativo. O problema deixou de ser “código bonito”; virou testabilidade e manutenção.

Revise a estrutura atual sem reescrever tudo. Quero separar apenas o necessário para que as regras de empréstimo e devolução possam ser testadas sem executar input(). Identifique responsabilidades misturadas e proponha uma divisão mínima de arquivos. Preserve o comportamento já aprovado.

Uma divisão possível, depois de revisada pela equipe, é:

projeto_emprestimos/
├── app.py
├── emprestimos.py
├── dados/
│   └── equipamentos.json
└── test_emprestimos.py

Agora a refatoração tem motivo

app.py cuida da interação. emprestimos.py concentra regras que podem ser chamadas e testadas. Não dividimos arquivos para “parecer profissional”; dividimos porque uma necessidade concreta apareceu.

11. Os testes deixam de ser uma tabela no caderno e passam a proteger mudanças futuras

Os casos que você escreveu antes agora podem virar testes automatizados. Um deles registra justamente o bug que já aconteceu:

def test_devolver_libera_equipamento():
    dados = criar_dados_iniciais()

    emprestar(dados, "NB01", "Ana")
    devolver(dados, "NB01")

    assert dados["NB01"]["disponivel"] is True
    assert dados["NB01"]["emprestado_para"] is None

Esse teste não existe para agradar a ferramenta. Ele existe para impedir que uma mudança futura faça o mesmo defeito voltar silenciosamente.

Com base nas regras já aprovadas do projeto, proponha testes para: empréstimo válido, segundo empréstimo recusado, devolução, código inexistente e normalização do código. Para cada teste, explique qual regra ele protege. Não crie regras novas.

Teste não substitui requisito

A IA pode sugerir casos. Quem define o resultado correto continua sendo a regra do sistema que você conhece e aprovou.

12. “Na minha máquina funciona” — agora o problema é ambiente, não lógica

Um colega organiza os testes com pytest. No computador dele tudo passa. No laboratório da escola aparece:

ModuleNotFoundError: No module named 'pytest'

A regra de empréstimo não ficou errada. O ambiente não possui a dependência usada para executar os testes.

Diagnóstico sem contexto

Por que meu teste não funciona?

Contexto que muda a resposta

Os testes rodam em outro computador, mas neste laboratório Python 3.12 informa ModuleNotFoundError: No module named 'pytest'. Antes de mandar instalar qualquer coisa, explique o que preciso verificar sobre interpretador selecionado, ambiente virtual, instalação do pacote e registro de dependências do projeto.

Versão do Python, interpretador selecionado, ambiente virtual e dependências fazem parte do contexto técnico. Código idêntico pode se comportar de forma diferente quando esse contexto muda.

13. O projeto agora contém dados de pessoas — e nem todo contexto deve ser enviado para a IA

Os testes da turma começam a usar nomes reais de alunos e alguém pensa em colar o arquivo equipamentos.json inteiro numa conversa para pedir ajuda. A IA não precisa receber identidades reais para entender a regra do programa.

Contexto desnecessário

"emprestado_para": "Nome completo do aluno real"

Mesmo problema, menos exposição

"emprestado_para": "ALUNO_TESTE_01"
  • Use dados fictícios ou anonimizados nos exemplos enviados à IA.
  • Compartilhe apenas os arquivos e trechos necessários para o problema.
  • Se futuramente houver API, nunca envie chaves, tokens ou arquivo .env com valores reais.
  • Se um segredo real for exposto, apagar a conversa não basta: trate o segredo como comprometido e siga o procedimento de revogação do serviço.

Mais contexto não significa mandar tudo

Contexto bom é o que ajuda a resolver a tarefa. Informação pessoal, segredo e arquivo irrelevante só aumentam risco.

14. O professor pede uma revisão antes de outra turma assumir o projeto

Agora existe algo concreto para revisar: regras separadas em emprestimos.py, interface em app.py, persistência e testes. A revisão deixa de ser “deixe meu código melhor”.

Revise este projeto sem editar ainda. Organize os achados em: - CORREÇÃO: comportamento que pode estar errado; - LEGIBILIDADE: algo que dificulta entender; - DUPLICAÇÃO: lógica repetida que aumenta risco de inconsistência; - TRATAMENTO DE ERROS: falhas que hoje não têm resposta adequada; - TESTABILIDADE: pontos difíceis de isolar ou testar. Para cada achado, cite o arquivo e o trecho. Não proponha mudanças apenas cosméticas.

Depois da revisão, escolha uma melhoria com justificativa, altere pouco e rode novamente os testes já existentes.

Refatoração profissional

Refatorar é melhorar a estrutura preservando comportamento. Se uma regra mudou sem intenção, não foi apenas refatoração.

15. Sexta-feira — uma IA com acesso ao repositório pode agir, não apenas sugerir

Até aqui você poderia copiar trechos para um chatbot. Agora imagine um agente de programação conectado ao projeto. Ele consegue localizar arquivos, editá-los e executar testes. Isso é poderoso, mas amplia o impacto de uma instrução ruim.

Novo pedido do laboratório

Além de emprestar e devolver, o sistema deve permitir reservar um equipamento disponível para uma aula futura. A reserva não pode marcar o equipamento como emprestado e deve poder ser cancelada.

Delegação sem controle

Adicione reservas no projeto inteiro e corrija o que precisar.

Agente com escopo verificável

Antes de editar, analise o projeto e liste quais arquivos precisam mudar para implementar reserva e cancelamento de reserva. Explique por quê. Não altere nada ainda. Depois da minha aprovação, faça somente as mudanças necessárias. Preserve empréstimo, devolução e persistência existentes. Acrescente testes para as novas regras e execute também os testes antigos. Ao final, mostre resumo do diff, testes executados, riscos restantes e qualquer decisão de requisito que ainda precise de resposta humana.
  • Trabalhe em branch separada.
  • Revise arquivos que o agente pretende alterar antes de autorizar.
  • Leia o diff; não aceite apenas “concluído”.
  • Execute testes antigos e novos.
  • Desconfie de dependências ou APIs novas que não foram solicitadas.
  • Prefira mudanças reversíveis e escopo pequeno.

16. Laboratório final — implemente a reserva sem terceirizar a decisão

Agora você assume o fluxo completo. Pode usar um chatbot ou agente de programação, mas cada etapa tem uma entrega que você precisa avaliar.

Etapa A — escreva as regras antes da IA

Defina com suas palavras: quando uma reserva pode ser criada, o que acontece se o equipamento já estiver emprestado ou reservado, e como uma reserva é cancelada.

Etapa B — peça perguntas sobre lacunas

Estas são minhas regras de reserva. Antes de propor código, identifique no máximo cinco decisões que ainda estejam ambíguas e que possam alterar a implementação. Não invente respostas para elas.

Etapa C — transforme regras em testes

Inclua pelo menos: reservar disponível, impedir segunda reserva, impedir reserva de emprestado, cancelar reserva e comprovar que empréstimo/devolução continuam funcionando.

Etapa D — planeje a alteração

Com base apenas nas regras aprovadas e no projeto atual, liste arquivos e funções que precisam mudar. Preserve o restante. Não escreva código ainda.

Etapa E — implemente pouco e revise o diff

Autorize a mudança somente depois de entender o plano. Compare antes/depois e procure requisito novo que ninguém pediu.

Etapa F — execute os testes e investigue qualquer falha

Não peça para “fazer passar”. Primeiro descubra qual regra, teste ou implementação está errada.

Etapa G — explique sem a IA

Feche a conversa e responda: quais arquivos mudaram, qual estado representa uma reserva, como ela é cancelada e quais testes comprovam que as regras antigas continuam válidas?

Critério de conclusão

Você não terminou quando a ferramenta escreveu o código. Terminou quando consegue defender a mudança com requisitos, diff, testes e explicação própria.

17. Desafio de transferência — aplique o processo em um código seu

Escolha um programa pequeno que você realmente consiga executar — em Python, JavaScript, Java, VisuAlg ou outra linguagem estudada. Não copie o projeto do laboratório; transfira o método.

  1. Explique o comportamento atual sem IA.
  2. Execute e registre pelo menos dois casos reais.
  3. Peça à IA para mapear o código sem alterá-lo.
  4. Defina uma mudança pequena e escreva o comportamento esperado.
  5. Crie casos de teste antes da mudança.
  6. Peça um plano antes de pedir código.
  7. Faça ou autorize uma alteração limitada.
  8. Compare antes/depois e execute os testes.
  9. Se houver falha, investigue com evidência antes de corrigir.
  10. Explique você mesmo o que mudou e como comprovou.

Se a única explicação for “a IA fez”

Volte uma etapa. O propósito do módulo é usar IA para aumentar sua capacidade de desenvolver e revisar software — não esconder o desenvolvimento atrás da ferramenta.

A ideia que fecha o módulo

Programar com IA não é trocar conhecimento por velocidade. É usar velocidade sem abrir mão de entendimento, evidência e controle.
