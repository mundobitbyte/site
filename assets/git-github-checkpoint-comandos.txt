MUNDO BIT BYTE — GIT E GITHUB
CHECKPOINT DE COMANDOS — CAFÉ AURORA

Objetivo
Este arquivo reúne, em ordem, os comandos usados no módulo para quem precisa recuperar a prática completa.
Ele NÃO é um arquivo de lote executável.

COMO USAR
1. Leia cada bloco na ordem.
2. Copie e cole os comandos no Git CMD.
3. Sempre que encontrar um trecho entre <<< >>>, pare e substitua pelo valor do seu caso.
4. Não copie cegamente comandos de HASH, URL ou nome de branch.
5. Quando houver uma etapa no navegador, faça essa etapa antes de continuar.

============================================================

git --version

git config --global user.name "<<<SEU NOME>>>"

git config --global user.name
git config --global user.email

Resultado esperado:
- Git reconhecido pelo Windows.
- Seu nome e e-mail configurados.

============================================================
CHECKPOINT 01 — ESCOLHER ONDE TRABALHAR
============================================================

Escolha APENAS UMA opção.

OPÇÃO A — usuário local do computador

cd /d "%USERPROFILE%"

OPÇÃO B — sua pasta na rede

Formato genérico:

pushd \\<<<SERVIDOR>>>\<<<PASTA>>>\<<<SEU-USUARIO>>>

Exemplo concreto de entrada na pasta-base da rede:

pushd \\10.66.53.1\Publica\mtec2025\nome.sobrenome

Se as pastas já existirem e você quiser entrar diretamente no projeto:

pushd \\10.66.53.1\Publica\mtec2025\nome.sobrenome\meus-repositorios\site-cafe-aurora

Substitua nome.sobrenome pelo nome da sua pasta na rede.

Neste primeiro percurso, use a pasta-base e depois crie as pastas abaixo.

Depois, nas duas opções:

mkdir meus-repositorios
cd meus-repositorios
mkdir site-cafe-aurora
cd site-cafe-aurora
cd
dir

ANTES DE CONTINUAR:
- o caminho atual deve terminar em site-cafe-aurora;
- se aparecer apenas C:\Users\seuUsuario, você ainda não entrou no projeto;
- NÃO execute git init fora da pasta site-cafe-aurora.

SE VOCÊ ESCOLHEU A PASTA NA REDE:
Quando o Git começar a trabalhar nesse repositório, ele pode apresentar detected dubious ownership ou uma mensagem sobre safe.directory.
Isso acontece porque o Git faz uma verificação de segurança e pode não reconhecer automaticamente a propriedade de alguns caminhos de rede.

Se esse erro aparecer depois do git init, use o caminho UNC real com barras /, mesmo no Windows.

Procedimento validado:

git config --global --unset-all safe.directory

git config --global --add safe.directory "//10.66.53.1/Publica/mtec2025/nome.sobrenome/meus-repositorios/site-cafe-aurora"

git status

O que cada comando faz:
- --unset-all safe.directory remove os registros anteriores de diretórios autorizados;
- --add safe.directory autoriza especificamente o repositório indicado;
- git status confirma se o Git reconheceu corretamente o repositório;
- substitua nome.sobrenome pelo nome da sua pasta na rede;
- no caminho usado pelo Git, mantenha as barras /;
- NÃO use safe.directory "*". Autorize somente o repositório necessário.

Resultado esperado:
- Você está dentro de site-cafe-aurora.
- Se houve bloqueio de segurança na rede, o repositório específico foi autorizado.

============================================================
CHECKPOINT 02 — INICIAR O REPOSITÓRIO
============================================================

Confirme novamente o local:

cd

Só continue se o caminho terminar em site-cafe-aurora.

Agora:

git init

echo Sabado: 08:00-18:00 > horario.txt
type horario.txt

git status

Se estiver usando a pasta na rede e aparecer detected dubious ownership ou safe.directory, volte ao CHECKPOINT 01 e aplique o procedimento validado antes de continuar.

SE VOCÊ EXECUTOU git init NA PASTA ERRADA:

Não existe um comando git deinit. Em um repositório comum criado com git init, o controle Git fica na pasta interna .git.

Primeiro descubra qual pasta o Git considera a raiz do repositório:

git rev-parse --show-toplevel

Confira com cuidado o caminho mostrado. Entre exatamente nessa pasta e verifique a existência de .git:

dir /a

SOMENTE se tiver certeza de que esse repositório foi criado por engano, no Git CMD/CMD execute:

rmdir /s /q .git

Depois confira:

git status

Resultado esperado nesse caso:
fatal: not a git repository

Isso significa que a pasta voltou a ser uma pasta comum.

ATENÇÃO:
- os arquivos comuns da pasta permanecem;
- o histórico Git local, branches locais, configuração de remoto, área de preparação e demais dados guardados em .git são apagados;
- se esse histórico existir apenas nesse computador, ele será perdido;
- um repositório existente no GitHub NÃO é apagado por esse comando;
- não use rmdir /s /q .git dentro do repositório correto que você pretende continuar versionando.

Exemplo de um erro comum:

C:\Users\lenovo>git init

Se C:\Users\lenovo virou repositório por engano, volte exatamente para essa pasta, confirme .git com dir /a e só então remova .git.
Depois entre em site-cafe-aurora e execute git init no local correto.

Depois continue:

echo teste de horario > rascunho.tmp
echo *.tmp > .gitignore
git status

Resultado esperado:
- horario.txt aparece como arquivo ainda não registrado.
- rascunho.tmp deixa de aparecer por causa do .gitignore.

============================================================
CHECKPOINT 04 — INVESTIGAR O ERRO
============================================================

git log --oneline

PARE AQUI.
Copie os hashes reais mostrados no seu computador.

Veja o commit suspeito:

git show <<<HASH-DO-COMMIT-DO-ERRO>>>

Compare o commit anterior com o commit do erro:

git diff <<<HASH-ANTES-DO-ERRO>>> <<<HASH-DO-ERRO>>>

Resultado esperado:
- Você consegue localizar a mudança de 18h para 20h.

============================================================
CHECKPOINT 05 — CORRIGIR UM COMMIT ERRADO
============================================================

git status
git log --oneline

git revert --no-edit HEAD

type horario.txt
git log --oneline
git status

Resultado esperado:
- O horário volta para 18h.
- O commit errado continua no histórico.
- Um novo commit registra a correção.

CHECKPOINT 06 — CORRIGIR ANTES DO COMMIT
============================================================

git status

git restore --staged avisos.txt
git status

git restore avisos.txt
git status

Resultado esperado:
- Nenhuma dessas tentativas entra no histórico.

============================================================
CHECKPOINT 08 — RECUPERAR O CONTEÚDO DE UMA VERSÃO
============================================================

Crie o teste de domingo:

echo Domingo: 09:00-14:00 >> horario.txt
echo Programacao especial de domingo >> avisos.txt

git add horario.txt avisos.txt
git commit -m "Testa programacao de domingo"
git status
git log --oneline

PARE AQUI.
O commit logo abaixo de "Testa programacao de domingo" é o estado aprovado anterior.
Copie o hash dele.

git show <<<HASH-APROVADO>>>

git status
git restore --source=<<<HASH-APROVADO>>> -- .
git status
git diff

git add -A
git commit -m "Cancela teste de domingo e retoma versao aprovada"
git status
git log --oneline

Resultado esperado:
- Os arquivos voltam ao conteúdo anterior ao teste.
- O histórico continua preservado.

============================================================
CHECKPOINT 09 — CRIAR UMA BRANCH DE TESTE
============================================================

git status
git branch --show-current

ANOTE o nome mostrado. Neste arquivo chamaremos de <<<BRANCH-PRINCIPAL>>>.

git switch -c teste-reservas

echo Reservas antecipadas: teste interno > reservas.txt
git add reservas.txt
git commit -m "Testa recurso de reservas"
git status

git switch <<<BRANCH-PRINCIPAL>>>
dir

git switch teste-reservas
type reservas.txt

git switch <<<BRANCH-PRINCIPAL>>>
git branch

Resultado esperado:
- teste-reservas existe localmente.
- reservas.txt não faz parte da branch principal.

============================================================
CHECKPOINT 10 — VISITAR O PASSADO SEM ALTERÁ-LO
============================================================

git status
git branch --show-current
git log --oneline

Escolha um commit antigo em que avisos.txt já existia.

git switch --detach <<<HASH-ANTIGO>>>

type horario.txt
type avisos.txt
git status

Volte para a principal:

git switch <<<BRANCH-PRINCIPAL>>>
git status

Resultado esperado:
- Você viu uma versão antiga sem criar commit nem alterar a branch principal.

CHECKPOINT 11 — CRIAR O REPOSITÓRIO NO GITHUB
============================================================

============================================================
CHECKPOINT 18 — INTEGRAR A BRANCH APROVADA
============================================================

Na branch principal:

git status
git pull

git merge teste-reservas

type reservas.txt
git status

git push

Depois de confirmar que tudo foi integrado:

git branch -d teste-reservas
git push origin --delete teste-reservas

Resultado esperado:
- reservas.txt faz parte da branch principal.
- A branch de teste pode ser encerrada sem perder seus commits integrados.

============================================================

git status

Pergunte sempre:
- Estou na pasta certa?
- Estou na branch certa?
- Há alterações locais pendentes?
- O remoto está configurado corretamente?
- Quem possui a versão mais nova: meu computador ou o GitHub?
