O pedido ganha um caminho

No capítulo anterior, o cliente passou a conferir o pedido inteiro. Isso resolveu a revisão, mas revelou uma nova limitação: identidade, produtos, dados do cliente, endereço e revisão aparecem em sequência na mesma tela.

A informação está correta. O problema agora é o percurso.

Escolher produtos → informar dados → informar endereço → revisar.→O aplicativo já possui etapas diferentes. Falta transformá-las em um caminho claro.
Construa e confira

1. Antes de programar, observe o fluxo

Pelo olhar do usuário, essas partes não precisam aparecer todas ao mesmo tempo. Ele pode concluir uma etapa e avançar para a próxima.

1 Produtos→↓→2 Dados do cliente→↓→3 Endereço de entrega→↓→4 Revisão do pedido

Agora existe uma razão concreta para usar navegação entre telas.

Construa e confira

2. Uma biblioteca passa a ser necessária

Até aqui, tudo cabia em componentes do próprio React Native. Para criar um fluxo de telas com histórico, botão de voltar e transições, usaremos React Navigation com o navegador Native Stack.

•@react-navigation/native fornece a estrutura central de navegação;

•@react-navigation/native-stack fornece a pilha de telas;

•react-native-screens e react-native-safe-area-context são dependências usadas pelo navegador.

No Snack, abra Dependencies, use Add Dependency e adicione @react-navigation/native, @react-navigation/native-stack, react-native-screens e react-native-safe-area-context. Confirme que os quatro pacotes aparecem na lista antes de continuar.

Construa e confira

3. O estado precisa sobreviver à troca de tela

Se cada tela criasse sua própria cópia de nome, endereço ou itens, voltar e avançar poderia produzir informações desencontradas.

Pedido.js já é o dono comum dos dados. Vamos preservar esse papel e transformá-lo em um provedor de contexto para as telas.

Pedido continua guardando a memória.
As telas mudam.
Os dados permanecem.

Aqui surge React.createContext e React.useContext. Não porque precisamos estudar Context isoladamente, mas porque várias telas precisam acessar o mesmo pedido.

components/Pedido.js - arquivo completo; ajuste as linhas em negrito
import * as React from 'react';

export const ContextoPedido = React.createContext();

const produtos = [
  {
    id: 1,
    nome: 'Água mineral 20 L',
    descricao: 'Galão retornável de água mineral.',
    preco: 20,
  },
  {
    id: 2,
    nome: 'Gás 13 kg',
    descricao: 'Botijão residencial de 13 kg.',
    preco: 100,
  },
];
export default function Pedido(props) {
  const [itensPedido, setItensPedido] = React.useState([]);
  const [nome, setNome] = React.useState('');
  const [telefone, setTelefone] = React.useState('');
  const [rua, setRua] = React.useState('');
  const [numero, setNumero] = React.useState('');
  const [bairro, setBairro] = React.useState('');
  const [complemento, setComplemento] = React.useState('');

  const valor = {
    produtos,
    itensPedido,
    setItensPedido,
    nome,
    setNome,
    telefone,
    setTelefone,
    rua,
    setRua,
    numero,
    setNumero,
    bairro,
    setBairro,
    complemento,
    setComplemento,
  };

  return (
    <ContextoPedido.Provider value={valor}>
      {props.children}
    </ContextoPedido.Provider>
  );
}

O componente Pedido agora envolve outras partes da aplicação e disponibiliza um único objeto com todo o estado necessário.

Construa e confira

4. Surge uma nova pasta: screens

Até agora usamos components porque construíamos partes reutilizáveis da interface. Agora o projeto ganhou algo diferente: telas completas.

components/ → partes da interface→screens/ → etapas completas do fluxo

Crie a pasta screens. Nela teremos quatro arquivos:

•TelaProdutos.js

•TelaCliente.js

•TelaEndereco.js

•TelaRevisao.js

Essa organização não existia antes porque o projeto ainda não precisava dela.

Construa e confira

5. App.js passa a conhecer as rotas

Agora App.js deixa de renderizar diretamente uma tela longa. Ele passa a registrar o caminho disponível no aplicativo.

App.js - novo estado completo; digite/ajuste o conteúdo em negrito
import * as React from 'react';
import { NavigationContainer } from '@react-navigation/native';
import { createNativeStackNavigator } from '@react-navigation/native-stack';

import Pedido from './components/Pedido';
import TelaProdutos from './screens/TelaProdutos';
import TelaCliente from './screens/TelaCliente';
import TelaEndereco from './screens/TelaEndereco';
import TelaRevisao from './screens/TelaRevisao';

const Stack = createNativeStackNavigator();

export default function App() {
  return (
    <NavigationContainer>
      <Pedido>
        <Stack.Navigator initialRouteName="Produtos">
          <Stack.Screen
            name="Produtos"
            component={TelaProdutos}
            options={{ title: 'Produtos' }}
          />
          <Stack.Screen
            name="Cliente"
            component={TelaCliente}
            options={{ title: 'Dados do cliente' }}
          />
          <Stack.Screen
            name="Endereco"
            component={TelaEndereco}
            options={{ title: 'Endereço de entrega' }}
          />
          <Stack.Screen
            name="Revisao"
            component={TelaRevisao}
            options={{ title: 'Revisão do pedido' }}
          />
        </Stack.Navigator>
      </Pedido>
    </NavigationContainer>
  );
}

Linhas destacadas são as que entram ou mudam nesta etapa

NavigationContainer envolve a árvore de navegação. Stack.Navigator organiza a pilha de telas. Cada Stack.Screen associa um nome de rota a um componente de tela.

Produtos → Cliente → Endereco → Revisao
Construa e confira

6. A primeira tela mantém a identidade e os produtos

A primeira etapa precisa mostrar a empresa e permitir que o cliente escolha os produtos. No final, o botão Continuar leva para os dados do cliente.

screens/TelaProdutos.js - arquivo novo; digite todo o conteúdo em negrito
import * as React from 'react';
import {
  View,
  ScrollView,
  Button,
  StyleSheet,
} from 'react-native';

import IdentidadeEmpresa from '../components/IdentidadeEmpresa';
import Produtos from '../components/Produtos';
import { ContextoPedido } from '../components/Pedido';

export default function TelaProdutos({ navigation }) {
  const pedido = React.useContext(ContextoPedido);

  return (
    <ScrollView contentContainerStyle={styles.conteudo}>
      <View style={styles.cartao}>
        <IdentidadeEmpresa />
        <Produtos
          produtos={pedido.produtos}
          itensPedido={pedido.itensPedido}
          onAtualizarItens={pedido.setItensPedido}
        />

        <View style={styles.acoes}>
          <Button
            title="Continuar"
            onPress={() => navigation.navigate('Cliente')}
          />
        </View>
      </View>
    </ScrollView>
  );
}
const styles = StyleSheet.create({
  conteudo: {
    padding: 16,
    backgroundColor: '#eef3f7',
    flexGrow: 1,
  },
  cartao: {
    backgroundColor: '#ffffff',
    borderRadius: 16,
    padding: 20,
  },
  acoes: {
    marginTop: 20,
  },
});

Linhas destacadas são as que entram ou mudam nesta etapa

Como TelaProdutos foi registrada no Native Stack, ela recebe navigation diretamente. A chamada navigation.navigate('Cliente') pede ao navegador que abra a rota Cliente.

React.useContext(ContextoPedido) recupera a mesma memória que Pedido mantém acima das telas.

10. Faça o teste que realmente importa

1.Na tela Produtos, escolha água e gás e ajuste quantidades.

2.Toque em Continuar.

3.Preencha nome e telefone.

4.Avance para Endereço e preencha rua, número e bairro.

5.Avance para Revisão.

6.Confirme que itens, quantidades, total, cliente e endereço continuam corretos.

7.Use o botão de voltar do cabeçalho para retornar a uma etapa anterior.

Trocar de tela não pode significar perder o pedido.

Construa e confira

11. O que realmente aprendemos sobre navegação

•uma rota representa uma tela registrada no navegador;

•NavigationContainer mantém a árvore de navegação;

•Native Stack organiza o histórico das telas visitadas;

•navigation.navigate abre uma rota pelo nome;

•o histórico permite voltar para a tela anterior;

•estado e navegação são problemas diferentes: a tela pode mudar enquanto os dados permanecem;

•Context permite que telas diferentes consultem e alterem a mesma memória do pedido.

O mais importante não é decorar os nomes. É perceber por que a aplicação precisou de um caminho entre etapas sem perder o que já havia sido preenchido.

15. O próximo problema já apareceu

O cliente agora consegue percorrer o pedido em etapas, revisar tudo e voltar para corrigir informações.

Mas existe uma diferença decisiva entre montar um pedido na tela e fazer esse pedido chegar à Santa Filomena Água & Gás.

O pedido está pronto no aplicativo. Para onde ele vai quando o cliente confirmar?

Essa pergunta abre o último capítulo: o aplicativo precisará enviar dados para fora dele, receber uma resposta e informar ao usuário se a operação deu certo.
