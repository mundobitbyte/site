Construa e confira

1. Agora precisamos conversar com outro sistema

Um aplicativo real normalmente envia dados pela rede para algum serviço: uma API, um servidor ou outro sistema capaz de receber e processar o pedido.

React Native já disponibiliza a API Fetch para realizar requisições de rede. Neste curso, vamos usá-la com HTTPS e com uma API pública criada para testes.

Aplicativo → requisição HTTP → API → resposta → aplicativo
Construa e confira

2. O teste precisa ser seguro e honesto

Não vamos fingir que existe um servidor real da Santa Filomena Água & Gás. Usaremos JSONPlaceholder, uma API pública para testes e protótipos.

Ela aceita uma requisição POST e devolve uma resposta como se um recurso tivesse sido criado. O próprio serviço informa que essa criação é simulada e não fica realmente persistida.

Neste capítulo, 'pedido enviado' significa: o aplicativo conseguiu realizar uma requisição de demonstração e recebeu uma resposta.

Construa e confira

3. A comunicação externa ganha um lugar próprio

Até agora, components guarda partes da interface e screens guarda telas. A comunicação com um serviço externo é outra responsabilidade.

components/ → interface reutilizável→screens/ → telas completas→services/ → comunicação com serviços externos

Crie a pasta services e, dentro dela, o arquivo pedidoApi.js.

services/pedidoApi.js - arquivo novo; digite todo o conteúdo em negrito
const URL_PEDIDOS =
  'https://jsonplaceholder.typicode.com/posts';

export async function enviarPedido(pedido) {
  const resposta = await fetch(URL_PEDIDOS, {
    method: 'POST',
    headers: {
      Accept: 'application/json',
      'Content-Type': 'application/json; charset=UTF-8',
    },
    body: JSON.stringify(pedido),
  });

  if (!resposta.ok) {
    throw new Error(
      `Falha no envio. Status: ${resposta.status}`
    );
  }

  return resposta.json();
}

Construa e confira

4. Leia a requisição antes de decorar

•fetch recebe a URL do serviço e as opções da requisição;

•method: 'POST' indica que estamos enviando dados;

•Content-Type informa que o corpo está em JSON;

•JSON.stringify transforma o objeto JavaScript em texto JSON para envio;

•await espera a resposta antes de continuar;

•response.ok precisa ser verificado porque um status HTTP de erro não vira automaticamente uma exceção;

•response.json() lê o corpo da resposta como JSON.

A função foi marcada como async porque contém operações assíncronas aguardadas com await.

Construa e confira

5. Antes de enviar, o pedido precisa estar pronto

Não faz sentido disparar a requisição com nenhum produto, sem nome, sem telefone ou sem endereço básico.

A tela de revisão já conhece todas essas informações. Portanto, a condição de envio pode ser calculada ali, sem criar outro estado duplicado.

Pedido pronto = há item + nome + telefone + rua + número + bairro

Complemento continua opcional.

Construa e confira

6. A tela de revisão ganha a ação final

TelaRevisao agora precisará de três capacidades novas: validar se o pedido pode ser enviado, mostrar que a requisição está em andamento e apresentar o resultado.

O estado enviando é local porque somente esta tela precisa saber se está aguardando a rede. Da mesma forma, mensagemEnvio só interessa à experiência desta tela.

screens/TelaRevisao.js - arquivo completo; nesta etapa, substitua pelo estado abaixo
import * as React from 'react';
import {
  View,
  ScrollView,
  Button,
  Text,
  ActivityIndicator,
  StyleSheet,
} from 'react-native';

import RevisaoPedido from '../components/RevisaoPedido';
import { ContextoPedido } from '../components/Pedido';
import { enviarPedido } from '../services/pedidoApi';

export default function TelaRevisao({ navigation }) {
  const pedido = React.useContext(ContextoPedido);
  const [enviando, setEnviando] = React.useState(false);
  const [mensagemEnvio, setMensagemEnvio] = React.useState('');
  const pedidoPronto =
    pedido.itensPedido.length > 0 &&
    pedido.nome.trim() !== '' &&
    pedido.telefone.trim() !== '' &&
    pedido.rua.trim() !== '' &&
    pedido.numero.trim() !== '' &&
    pedido.bairro.trim() !== '';

  async function confirmarEnvio() {
    if (!pedidoPronto) {
      setMensagemEnvio(
        'Complete produtos, cliente e endereço antes de enviar.'
      );
      return;
    }
    const dadosParaEnvio = {
      cliente: {
        nome: pedido.nome,
        telefone: pedido.telefone,
      },
      entrega: {
        rua: pedido.rua,
        numero: pedido.numero,
        bairro: pedido.bairro,
        complemento: pedido.complemento,
      },
      itens: pedido.itensPedido,
    };

    try {
      setEnviando(true);
      setMensagemEnvio('');
      const resposta = await enviarPedido(dadosParaEnvio);

      setMensagemEnvio(
        `Envio de demonstração concluído. ` +
        `Protocolo simulado: ${resposta.id}.`
      );
    } catch (erro) {
      setMensagemEnvio(
        'Não foi possível enviar o pedido. Tente novamente.'
      );
    } finally {
      setEnviando(false);
    }
  }
  return (
    <ScrollView contentContainerStyle={styles.conteudo}>
      <View style={styles.cartao}>
        <RevisaoPedido
          produtos={pedido.produtos}
          itensPedido={pedido.itensPedido}
          nome={pedido.nome}
          telefone={pedido.telefone}
          rua={pedido.rua}
          numero={pedido.numero}
          bairro={pedido.bairro}
          complemento={pedido.complemento}
        />

        {!pedidoPronto && (
          <Text style={styles.aviso}>
            Complete os dados obrigatórios antes do envio.
          </Text>
        )}
        {enviando && (
          <View style={styles.enviando}>
            <ActivityIndicator />
            <Text style={styles.textoEnviando}>
              Enviando pedido...
            </Text>
          </View>
        )}

        {mensagemEnvio !== '' && (
          <Text style={styles.mensagem}>
            {mensagemEnvio}
          </Text>
        )}
        <View style={styles.acoes}>
          <Button
            title={enviando ? 'Enviando...' : 'Enviar pedido'}
            onPress={confirmarEnvio}
            disabled={enviando}
          />
        </View>

        <View style={styles.acoesSecundarias}>
          <Button
            title="Voltar aos produtos"
            onPress={() => navigation.navigate('Produtos')}
          />
        </View>
      </View>
    </ScrollView>
  );
}
const styles = StyleSheet.create({
  conteudo: {
    padding: 16,
    backgroundColor: '#eef3f7',
    flexGrow: 1,
  },
  cartao: {
    backgroundColor: '#ffffff',
    borderRadius: 16,
    padding: 20,
  },
  aviso: {
    color: '#92400e',
    fontWeight: 'bold',
    marginTop: 16,
    textAlign: 'center',
  },
  enviando: {
    alignItems: 'center',
    marginTop: 16,
  },
  textoEnviando: {
    marginTop: 8,
  },
  mensagem: {
    color: '#374151',
    fontWeight: 'bold',
    marginTop: 16,
    textAlign: 'center',
  },
  acoes: {
    marginTop: 20,
  },
  acoesSecundarias: {
    marginTop: 12,
  },
});

Construa e confira

7. O que exatamente enviamos

Observe o objeto dadosParaEnvio. Ele contém três grupos:

•cliente: nome e telefone;

•entrega: rua, número, bairro e complemento;

•itens: ids e quantidades escolhidas.

Nesta demonstração, não enviamos o total calculado como fonte de verdade. Em um sistema comercial real, o servidor deveria consultar os preços atuais e calcular o valor final com regras próprias, em vez de confiar cegamente no valor enviado pelo aparelho.

Interface calcula para informar o usuário.
Servidor real deve validar novamente o pedido.

Construa e confira

8. Por que existem try, catch e finally

Rede não é instantânea nem garantida. A conexão pode falhar, o serviço pode responder com erro e o usuário precisa saber o que aconteceu.

•try contém a tentativa de envio;

•catch trata falhas e apresenta uma mensagem compreensível;

•finally é executado ao final da tentativa e encerra o estado enviando;

•ActivityIndicator mostra visualmente que existe uma operação em andamento.

O botão também muda para Enviando... durante a requisição, evitando múltiplos envios simultâneos pela mesma ação.

Construa e confira

10. Sucesso de demonstração não é venda real

Este ponto precisa ficar absolutamente claro. JSONPlaceholder é um serviço de teste. A resposta recebida demonstra que o aplicativo sabe realizar um POST e tratar a resposta.

Ela não cria um pedido real para a empresa e não deve ser usada como backend comercial.

Protótipo educacional concluído ≠ sistema comercial pronto para produção.

Construa e confira

11. O que seria necessário em produção

A arquitetura construída no curso já mostra o fluxo principal. Um produto comercial acrescentaria outras responsabilidades conforme a necessidade real.

•API própria da empresa ou serviço backend confiável;

•persistência em banco de dados;

•validação de preços, estoque e área de entrega no servidor;

•proteção dos dados pessoais e políticas de privacidade;

•autenticação quando necessária;

•tratamento mais completo de falhas e tentativas de reenvio;

•pagamento, caso o negócio exija pagamento no aplicativo;

•notificações e acompanhamento do pedido;

•testes automatizados e publicação nas lojas.

Esses assuntos não entram artificialmente neste curso porque o objetivo foi conduzir um iniciante do primeiro componente até um fluxo completo de pedido com comunicação de rede.

13. O que aprendemos neste capítulo

•fetch realiza requisições de rede em React Native;

•POST envia dados para um serviço;

•JSON.stringify prepara um objeto para um corpo JSON;

•async e await permitem aguardar operações assíncronas de forma legível;

•response.ok ajuda a distinguir uma resposta HTTP bem-sucedida de uma resposta de erro;

•try/catch/finally permite tratar sucesso, falha e encerramento de uma operação;

•ActivityIndicator comunica ao usuário que existe trabalho em andamento;

•estado local continua adequado para informações que pertencem apenas à própria tela;

•uma API de testes deve ser apresentada como simulação, nunca como backend real.

14. Confira antes de encerrar

•Existe a pasta services.

•pedidoApi.js exporta enviarPedido.

•A requisição usa HTTPS e método POST.

•O corpo enviado usa JSON.stringify.

•A resposta HTTP é verificada antes de ler o JSON.

•TelaRevisao valida os campos essenciais.

•Durante o envio, o usuário vê um indicador de atividade.

•Em caso de sucesso, aparece uma confirmação de demonstração.

•Em caso de falha, aparece uma mensagem compreensível.

•O texto deixa claro que nenhum pedido comercial real é persistido no serviço de teste.
